### FIND-TASK-001-3 — One path can count as two changed files

- **Source/status/gate:** `SRC-R2-1` — **CONFIRMED**; task contract (REQ-002 and TASK-001 scenario 1); **INCORRECT**.
- **Root cause and defect class:** `Listing::push` appends valid provider entries without checking that each canonical path appears only once in the logical listing. The resulting `Screen::source` is a list of entries, while REQ-002 counts changed *files*. Inconsistent provider input can represent one path twice.
- **Every sibling/sink:** `sample.rs:235-236` folds pages; `sample.rs:300-320` copies every eligible entry and records its patch result; `sample.rs:334-339` counts entries and treats a different vector index as another file. `main.rs:96-108` is the sole caller of `Listing::push`; `main.rs:156-188` is the sole caller of `Screen::new`/`qualifies` in production; `main.rs:197-244` can add the result to the sample; `main.rs:251-289` prints it. The provider parser at `src/github.rs:1367-1407` validates each file independently and preserves duplicates. There is no other sampler listing producer.
- **Reproduction:** Supply two valid `PullRequestFile` entries with the same `RelativePath` `src/a.py`, status `Modified`, and a one-line changed patch. `Listing::push` retains both; `Screen::new` creates two source entries and two `true` values; `plausible()` and `qualifies(|_| true)` return true because `source.len() == 2` and the two indices differ. `qualify` can likewise return `Some` if the base snapshot declares `src/a.py`. This is a traced no-network source path through the public command, independent of whether GitHub normally emits the inconsistency.
- **Consequence:** A one-file PR can qualify as a two-file PR; the sample and later withhold trials are wrong. The spec says provider inconsistency fails a run (INV-003), so silently accepting a duplicate is not a permitted input repair.
- **Smallest safe correction:** At the existing `Listing` fold owner, reject a repeated canonical path across and within pages as an unusable listing entry, using the sampler's existing run-failure path. Keep one listing and preserve provider order, patch omission classification, and path eligibility. Do not add a second listing, replay, snapshot check, or production-client change. Unique paths from the provider continue unchanged.
- **Closure proof:** One focused in-memory check with duplicate paths across pages and within one page must fail the run before `Screen::plausible`; distinct paths on the same pages must still qualify by the existing rule. The check should include equal paths with different status or patch to prove canonical path, rather than entry equality, is the key.

### FIND-TASK-001-4 — Invalid calendar and clock values pass timestamp validation

- **Source/status/gate:** `SRC-R2-2` and `SAMPLING-1` — **CONFIRMED**, merged as one root cause; task contract (REQ-002's fixed cutoff and unusable merge timestamp, TASK-001 scenario 2); **INCORRECT**.
- **Root cause and defect class:** `is_timestamp` at `sample.rs:205-214` verifies the twenty-byte shape and digits only. It does not validate month, Gregorian day including leap years, hour, minute, or second. The `String` values remain unvalidated despite the `MergedPr` invariant and are compared lexically as dates.
- **Every sibling/sink:** `Discovery::new` uses the helper for the cutoff at `sample.rs:140-149`; `Discovery::offer` uses it for update and merge times at `:160-188`; `Discovery::settled` orders by the accepted merge text at `:194-201`; `main.rs:213-230` uses these values to choose PRs. The only producers are the environment cutoff at `main.rs:253` and `ListedPr` JSON decoded in `Api::get` at `main.rs:73-87,216-225`; both can provide a correctly shaped impossible value.
- **Reproduction:** `is_timestamp("2026-02-30T25:61:61Z")` returns true: its digits and separators match `SHAPE`. Thus `Discovery::new` accepts an impossible configured cutoff; `Discovery::offer` accepts the same text as `updated_at` or `merged_at`, and a merged PR before a later cutoff reaches `pending`. The existing `discovery_fails_on_unusable_input` test covers only a short timestamp. This traced command path is enough to reproduce the defect without network access.
- **Consequence:** The run can advertise a nonexistent cutoff or merge time and select or order PRs using it instead of failing on unusable input.
- **Smallest safe correction:** Validate the actual Gregorian date and 24-hour clock once in the shared timestamp owner, retaining the fixed UTC `YYYY-MM-DDTHH:MM:SSZ` format needed for lexical order. Reuse that validator for cutoff, updated time, and merge time; keep the current error variants and ordering flow. No parser framework, new dependency, timezone flexibility, or host clock is needed.
- **Closure proof:** A focused no-network check rejects impossible day, non-leap February 29, month 0/13, and clock out of range at all three ingress points; it accepts a leap-day and ordinary GitHub UTC timestamps and preserves existing merge ordering.
