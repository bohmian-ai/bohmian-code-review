## Proposed findings

### DOMAIN-SAMPLING-1 — discovery page order is trusted without validation

- **Classification and obligation:** INCORRECT; REQ-002 requires the 50 most recently merged qualifying PRs in deterministic order, and INV-003 requires inconsistent provider input to fail the run.
- **Root cause and defect class:** `Api::select` assumes successive `sort=updated&direction=desc` pages are globally ordered by `updated_at`, then uses the current page's minimum as a safe settlement boundary without checking the next page against it. This is an unchecked cross-record ordering premise. `Discovery::offer` validates each record's timestamps and pairwise chronology, but has no memory of the preceding record's update time.
- **Sibling path:** `Api::select` derives `read_until` at `main.rs:227`, releases PRs through `Discovery::settled` at `main.rs:232` / `sample.rs:200-207`, qualifies them at `main.rs:233`, and returns immediately at 50 at `main.rs:235-237`. These are the sole discovery-order consumers and early-return sink. The R3 `merged_at <= updated_at` check at `sample.rs:178-183` does not establish order across PRs.
- **Reachable consequence:** If one 100-entry page contains 50 qualifying PRs updated January 5 and merged January 4 plus 50 unmerged PRs updated January 1, `read_until` is January 1 and the 50 merged PRs settle. `select` returns them. If the next provider page contains a qualifying PR updated January 10 and merged January 9, it is never read, despite outranking every selected PR. All individual timestamps and PR chronologies are valid. A shifted or inconsistent provider listing therefore produces a wrong sample instead of a run failure.
- **Testable correction:** At the existing discovery/page traversal owner, enforce nonincreasing update-time order across listed records and page boundaries before an early return can make the sample final. A newer later-page record must fail the run; preserve equal timestamps, the merge-time/PR-number tie rule, the one file listing per qualified PR, and the existing settlement behavior. A focused no-network check should feed a later page with a newer update and assert failure rather than a 50-PR success.

### DOMAIN-SAMPLING-2 — filtered merged PR commits escape identity validation

- **Classification and obligation:** INCORRECT; TASK-001 and REQ-002 say unusable PR identity fails the run. INV-003 says inconsistent provider input fails the run.
- **Root cause and defect class:** `Discovery::offer` validates base/head commit IDs only while constructing `MergedPr`, after returning for a merged PR on another branch or at/after the cutoff. The owner lets malformed provider identity pass as a valid filtered record. The affected sibling paths are both filter arms at `sample.rs:184-185`; the parsed record enters through `Api::get` and `Api::select` at `main.rs:220-229`. There is no later commit validation for those records.
- **Reachable consequence:** A listed merged PR with valid number and times, `merged_at >= cutoff`, and `head.sha = "nope"` returns `Ok(())` instead of `SampleError::UnusablePr`. The run can report a sample despite an unusable listed PR identity. A wrong-branch merged PR has the same result.
- **Testable correction:** Validate the listed merged PR's base/head IDs at the existing `Discovery::offer` input boundary before either filter returns, retaining the current error type and filters. A focused check should present bad IDs on both filtered paths and expect `UnusablePr`; valid filtered PRs should remain ignored. This uses the existing `ObjectSha` validator and needs no provider request or public API.

**Overall result: FAIL** — two proposed task-contract findings. The first directly threatens top-50 correctness; the second concerns the specified fail-on-unusable-input boundary.
