### FIND-TASK-001-3 — file-listing pages are reported as one request

- **Sources/status/gate:** `TASK-A-1`, `TASK-B-1`, `DOMAIN-PROVIDER-1`; **CLASS_INCOMPLETE**; task contract, [REQ-002](../../spec.md) and TASK-001 Scenario 3. This reopens the prior cost finding: the earlier correction separated per-PR and aggregate *listing* counts, but kept a fixed one-request unit. It did not preserve the actual HTTP page count through the report boundary.
- **Classification/root cause/defect class:** INCORRECT; `Api::listing` can issue up to 30 `pull_request_files` HTTP calls for one PR (`main.rs:196-213`), but returns only a `Listing`. `History::build` then increments `ListingReads` once per PR (`history.rs:119-124`), and `record` calls those counts production provider requests (`main.rs:552-559`). The owner shape loses the page-request unit between the provider read and report. This is the same inaccurate production-cost class as R1 FIND-TASK-001-3, with another dimension left unrepresented.
- **Sibling locations:** Both `Api::qualify`'s cached listings (`main.rs:289-306,433-463`) and history-only listings (`main.rs:458-465`) use the paginated owner. Cold cost at `main.rs:554`, incremental per-PR cost at `main.rs:556`, and incremental aggregate at `main.rs:557` all inherit listing counts in place of page requests. The merged-PR listing has its own page counter at `main.rs:416-424`; evaluation-only commit counts and review-time zero do not share the defect.
- **Obligation/evidence:** The approved spec calls these *provider requests*, including merged-PR listing **pages**, and requires one complete file listing per history PR (`spec.md:63-69`). One complete listing can require multiple requests. The fake explicitly expects PR 15 pages 1 and 2 (`main.rs:815-819`), yet asserts `cold_build: 1 + 11` (`main.rs:826-835`). PR 15 is among the 11 cold listings; that fixture made at least 13 cold HTTP calls: one merged-PR page plus 12 file-listing pages. The assertion accepts 12. A paginated incremental PR similarly consumes at least two requests while `per_merged_pr` stays 1 and the aggregate rises by one.
- **Consequence:** A successful report understates cold and incremental production request cost whenever a history PR listing spans pages, including the checked-in fake's cold case. `REQ-001`'s one *listing* per PR remains satisfied; the cost figure must account for the requests that complete that listing.
- **Correction boundary:** Restore page-request counts at the existing `Api::listing` / history accounting boundary and carry them through `Requests` into `record`, separately from the logical one-listing-per-PR retrieval invariant. Revise the prior fixed `per_merged_pr: 1` representation so the reported request cost reflects pages needed for the merged PR being measured; label any aggregate as an aggregate. Preserve listing reuse, all-pages completeness, cold depth, and no per-trial provider reads. Do not add a provider abstraction or change production APIs.
- **Focused closure proof:** In the existing no-network run test, assert cold requests count actual merged-PR and PR-file pages (13 in the present fixture), then make one incremental history PR span two pages and assert the per-PR and aggregate request costs include its second page. Check cached and history-only paths. The proof must still assert one logical listing per PR and no per-trial reads.

### FIND-TASK-001-5 — direct JSON reads have no body bound

- **Sources/status/gate:** `STANDARDS-1`; **CONFIRMED**; repository-standard gate, `AGENTS.md:23` and `architecture/bohmian-code-review-design.md:22` (outer pipeline owns bounded ingest). The direct reader was unbounded in the base, but `Api::get` was materially rewritten in the cumulative diff from `reqwest::Response::bytes()` to a new transport and chunk loop, so this is inside the touched owner, not unrelated debt.
- **Classification/root cause/defect class:** VIOLATION; the direct REST JSON reader appends every chunk to `Vec<u8>` without a size check (`main.rs:166-187`). Its shape bypasses the installed `GitHubClient`'s `RequestLimits::max_json_bytes` policy (`github.rs:200-225`), whose internal `read_bounded` rejects the next chunk before growth (`github.rs:1566-1589`).
- **Sibling locations/producers:** `Api::get` is the single owner. Its callers are repository metadata (`main.rs:407`), merged-PR listing pages (`main.rs:416-424`), and each sampled base-commit timestamp (`main.rs:260-279,322-324`). All receive potentially unbounded 200 response bodies from the direct `HttpTransport`; `live` uses `ReqwestTransport` (`main.rs:476-493`) and the fake supplies routed bodies (`main.rs:770-781`). `GitHubClient`'s file, tree, and blob reads use their own bounded path and are not siblings.
- **Reproduction/consequence:** Source trace: `run` → `Api::select` → any of these `get` callers → a 200 body streamed in chunks → unconditional `bytes.extend(chunk)` → JSON parse only after the whole body arrives. A response larger than the pipeline's default 32 MiB JSON bound is accepted into memory until transfer or allocation fails; the result can exceed the mandated bounded-ingest limit while the provider client enforces it elsewhere.
- **Correction boundary:** Bound the existing direct `Api::get` body using the already installed `RequestLimits::max_json_bytes`, checking each chunk before appending and returning a typed or clear size error. Keep its single-attempt, fail-on-non-200 behavior and the existing response decoding. The pipeline's private `read_bounded` cannot be called from this example; a small local check at the direct read owner suffices.
- **Focused closure proof:** Through the existing fake direct transport, return a valid 200 JSON body just above the configured bound for one `Api::get` caller and assert failure before full buffering/report emission; a body at the bound still decodes. Because every direct caller shares `get`, this covers repository metadata, PR pages, and commit-time reads without separate copies of the check.
