## Findings

### TASK-A-1 — INCORRECT: incomplete mass-edit listings bypass provider completeness

Root cause / defect class: `history::changed` classifies a mass edit before checking `Listing::truncated` or rejected entries. Owner shape: the `Option<Vec<RelativePath>>` return allows `None` to stand for a mass edit even when the listing is untrustworthy. Siblings: `Api::qualify` calls `changed` before `Screen::new`, so a truncated qualification listing is temporarily accepted as history (then `Screen::new` fails); `Api::select` reads only one page for uncached history PRs and accepts its `None` without further completeness check. Violates REQ-001 and INV-002's explicit missing/incomplete-response failure, and TASK-001 Scenario 3. A history PR with 100 visible files and `has_next=true` becomes a successful dropped mass edit; the test also explicitly accepts a truncated, rejected mass listing. The command can emit a report after an incomplete provider listing. Correction: reject incomplete or rejected listings before accepting a mass-edit classification, and prove the one-page history path fails on an advertised next page; read enough pages if the approved one-listing contract requires complete paths.

### TASK-A-2 — MISSING: no fake-provider proof of the real selection/read path

Root cause / defect class: the new `Api::select` path remains bound to `reqwest::Client`, `GitHubClient`, and the fixed `https://api.github.com` URL, while tests stop at pure `History::build` and fixed repository constants. Owner shape: this hardcoded network seam prevents a no-network fake provider from exercising the path that lists PRs, reuses qualification file listings, fetches sampled base commit times, and counts requests. Siblings: `Api::get`, `Api::listing`, and `Api::base_time` are the sinks for the same untested provider behavior. Violates AC-003 and TASK-001 Scenario 3's explicit fake-provider call-count and failure-path evidence. A regression that reads a listing twice or miscounts timestamp calls could pass the current tests. Correction: add the smallest fakeable seam around the example's provider reads and a no-network test that drives `Api::select` or its cohesive read workflow through a counting fake, including incomplete responses and one-read-per-PR assertions; avoid a broad generic provider layer.

### TASK-A-3 — INCORRECT: incremental production cost reports a cumulative run count as one update

Root cause / defect class: `record` maps `requests.history.incremental`, the number of historical PR listings fetched between cold point and newest sample base, directly to the singular `production.incremental_update` field. Owner shape: `Requests` stores only the evaluation interval's aggregate, not the per-merged-PR production update cost. Sibling: `cold_build` also mixes all evaluation discovery pages with cold-build reads, so its claimed production count needs the production listing boundary specified and verified. Violates REQ-002's requirement to state one file listing per merged PR for a production incremental update, separately from evaluation-only reads. In the included history test the field would be `4`, even though one merged-PR update needs one listing; report readers are given the wrong production unit. Correction: report one file listing per merged-PR update explicitly, retain historical aggregate under an evaluation-run label if useful, and assert the serialized production/evaluation cost categories with a multi-PR fixture.

Overall: **FAIL**.
