## Product boundary and success

`bohmian-code-review` supplies the code-understanding helpers for a future CodePal-like review service. The service will obtain tree and blob data from a Git provider API. This workspace accepts repository-relative paths, source bytes, and changed-line ranges already in memory. It must never clone, check out, or discover a Git repository; fetch source over a network; persist source or an index; call a model; publish comments; or implement cross-repository search. Test fixtures and build-time grammar compilation may use the filesystem. The runtime indexing and selection path may not.

The initial working journey is Snap CodePal's “Symbolic context and the two-pass file picker”: pass one parses caller-supplied source blobs with tree-sitter and builds a symbol-to-file map; pass two inspects changed source, finds referenced symbols, scores other files by symbol overlap, and chooses relevant code within a token budget. This implementation does **not** claim that a small set of supplied blobs is a complete repository index. The service decides which blobs to supply and verifies their repository, commit, path, and blob identity before calling the library.

## Public workflow and exact initial behavior

The facade owns an in-memory `SymbolicContextEngine`. It provides the following capabilities as synchronous Rust methods; method spelling may follow Rust conventions, but preserve these inputs, outputs, and guarantees:

1. `upsert_file(path, bytes) -> FileIndexOutcome`: validate the canonical repository-relative path; route and extract the supplied bytes through the ported extractor; replace that file's prior symbol postings atomically; return extracted symbols, references, and file-local diagnostics. An unsupported or malformed file reports its typed outcome without corrupting unrelated indexed files. The engine retains extracted facts and byte length, not `bytes`.
2. `remove_file(path)`: remove only that file's facts and postings. Repeating removal is harmless.
3. `lookup_symbol(name) -> Vec<SymbolHit>`: exact, case-sensitive simple and qualified-name lookup; include path, symbol kind, language, and source span. Multiple declarations remain multiple hits, ordered by path then source location then symbol ID.
4. `rank_changed_file(path, head_bytes, changed_lines) -> Vec<RankedFile>`: parse the full head-side changed blob; use declarations whose spans overlap a changed line and extracted references located on a changed line. Match their exact names and any extractor-provided qualified candidates against the symbol index. Exclude the changed file from secondary candidates. Count each distinct matched name once per candidate file; score is that count. Sort descending by score, then ascending canonical path. Return matched names and symbol spans as selection reasons. Do not invent fuzzy matches or treat a candidate hit as proven semantic resolution.
5. `build_context(changed_file, ranked_files, supplied_candidate_blobs, limits, token_count) -> ReviewContext`: include the supplied changed hunks first, then relevant symbol spans from ranked files. `token_count: Fn(&str) -> usize` is supplied by the future service so the library does not pick a model tokenizer. Enforce `max_files` and `max_tokens` before adding each span. Return selected paths, line ranges, source text, scores, reasons, token usage, and explicit omissions. Never silently truncate within a source span. If the changed hunk alone cannot fit, return a typed budget error; the service may split the diff and retry. Missing candidate blob input is reported explicitly rather than fetched by the library.

Use one-based line numbers at the public boundary, matching the extracted facts. Validate nonempty ascending changed-line ranges. Indexing must process files one at a time so full-repository source bytes need not coexist in memory; retained index memory may grow with extracted facts. This initial workflow analyzes head-side changed content. Return an explicit unsupported-input error for deletion-only changes rather than pretending to have analyzed them; base-side support belongs to a later reviewed change.

The future service owns the Git provider API, diff acquisition, blob identity checks, candidate blob fetching after ranking, the shared context store, review/summary/description model workflows, finding verification, feedback, and cross-repository Code Search. The facade returns a structured context value suitable for that shared store but does not implement the store.
