### FIND-TASK-007-1 — Warm capacity samples can measure different PR revisions

- **Sources/status:** `TASK-B-1`, `CAP-1`; merged as **CLASS_INCOMPLETE** under the prior ID. The R1 correction fixed the cold selector, but its shape pins only the snapshot. The same benchmark entrypoint still accepts a mutable PR number for every warm sample.
- **Gate/classification:** Task contract, `AC-007` (`changes/active/repo-parser/spec.md:121`), TASK-007 approach step 4 and acceptance criterion, and the written reproducibility rule (`architecture/bohmian-code-review-design.md:38`). `INCORRECT` fixed-commit benchmark proof.
- **Root cause/defect class:** The benchmark input is only partly immutable. `BCR_COMMIT` enters `ColdBuild::run_at` at `examples/live_pr.rs:101-106`, but the first and every warm measurement independently call `PrContext::run(identity, number)` at `:117,121`. Its `pin` reads the PR and paginated files anew (`src/pull_request.rs:324-353`). The report records the first context's `base`/`head` at `live_pr.rs:143-145`, but takes warm elapsed times from later calls at `:121-130,177-178` without checking their base/head. A PR update between calls can therefore mix distinct workloads while the report displays one PR revision. The fixed cold tree does not prevent this.
- **Siblings:** First and all warm calls in the single benchmark entrypoint; `evidence/TASK-007/s20-wyrd-pr1.json`, `bench-vscode.json`, `bench-rust.json`, and the three capacity rows in `tasks/TASK-007-integrated-pipeline-and-real-pr.md`. The ordinary `PrContext::run` caller is deliberately head-correct and must retain fresh PR pinning; this finding concerns only benchmark sample comparability. `s20-wyrd-pr91.json` is the separate negative S20 run, not a capacity row.
- **Reproduction:** Traced `mise run live:pr` (`mise.toml:65-70`) → `live_pr::run` → first and repeated `PrContext::run` → `PrContext::pin`. The first result's identity is emitted, but later `PrContextResult`s are discarded apart from elapsed time (`live_pr.rs:120-124`). If a PR moves between these calls, `pin` correctly returns the new head, so warm p50/p95 can reflect a different diff, overlay, and candidate set. The existing fake-provider test `snapshot::tests::fixed_commit_build_ignores_head_advance_and_run_follows_it` (`snapshot.rs:1711-1740`) proves only the cold commit selector; it does not exercise PR movement between warm calls.
- **Consequence:** The named warm p50/p95 and API-call totals cannot be attributed to one fixed workload; later reruns can also follow a different PR revision. Cold time, archive bytes, memory, and snapshot size are pinned by `BCR_COMMIT`; this finding does not reopen those parts of R1.
- **Smallest safe correction:** Keep production `PrContext::run` and its per-call pinning unchanged. In the opt-in capacity entrypoint, define one benchmark PR base/head input or observed identity and require every measured PR call to use that identity; fail a sample when it differs and record the pinned pair with the capacity row. Use the existing `PrContextResult.context` identity and GitHub's current PR reads; avoid a second PR implementation or persisted state. If a mutable real PR cannot supply repeatable evidence at those refs, replace only that capacity fixture with a stable one and rerun the affected row. Do not alter S20's normal live-PR behavior.
- **Focused closure proof:** A fake-provider benchmark check advances the PR between first and warm calls and shows that no p50/p95 report is accepted across revisions; a stable PR produces the intended measurements. Re-run or qualify each affected capacity row with exact cold commit/tree and PR base/head and prove all accepted samples share them.

### FIND-TASK-007-2 — Provider contract outcomes are recorded but not validated

- **Sources/status:** `PROV-1`; **CLASS_INCOMPLETE** under the prior controlled-provider finding. R1 supplied the missing command and a passing captured report, but the command's success result does not establish most named cases. The correction's report-only shape let the evidence gap recur.
- **Gate/classification:** Task contract, `REQ-017` (`spec.md:80`), `AC-006` (`spec.md:120`), and TASK-007-R1 acceptance for the controlled contract. `INCORRECT` executable contract validation.
- **Root cause/defect class:** `examples/provider_contract.rs::run` stores tree completeness/path counts at `:153-156`, archive byte count and gzip magic at `:162-173`, conditional status at `:199-214`, and response rate headers through `Recording::get` at `:61-75`. After printing the report at `:216-224`, its only semantic failure check is nonempty `without_patch` at `:225-228`. A truncated tree, `gzip_magic: false`, conditional status other than 304, or missing rate headers can all accompany exit 0. The GitHub client's blob SHA and identity checks do fail at their source owner, so they need no duplicate validator.
- **Siblings:** Recursive tree completeness and invalid-path result; archive redirect/shape and gzip result; conditional 304 result; required rate headers on API responses. The PR patch-omission case is already checked. All are one missing contract-result validation at `provider_contract::run`, not separate defects.
- **Reproduction:** Source trace: `mise run live:provider-contract` (`mise.toml:72-74`) invokes `run`; the case calls either return a response or append a JSON result; only `without_patch.is_empty()` decides semantic success. The checked-in `evidence/TASK-007/provider-contract-wyrd.json` actually records a nontruncated 3,210-entry tree, zero invalid paths, 302→200 archive with gzip magic, a 304 conditional observation, rate headers, and omitted patches. I parsed those case results directly. The *captured run* passes its named cases, but its zero exit is not a reliable validation proof on a later provider response.
- **Consequence:** A future controlled-provider run can be marked PASS even when a named compatibility case fails, undermining the pre-rollout check required by AC-006.
- **Smallest safe correction:** Keep `GitHubClient`, `ReqwestTransport`, the raw conditional observation boundary, and the captured-case format. Make the existing command reject failed named outcomes before returning success, using its recorded results or direct case values at the same owner. Check only obligations not already enforced by the client: complete usable recursive listing, archive redirect/shape and gzip, conditional 304, and expected rate headers. Preserve the stated local fake proof for 403/429 and GHES; do not exhaust a live quota or add production conditional-request support.
- **Focused closure proof:** One local transport-driven check supplies a failed outcome for each sibling class and proves nonzero status, then supplies valid outcomes and proves success; the existing captured live report remains evidence for the real provider. No new credentialed CI lane is needed.
