## Proposed finding

### CAP-1 — PR workload is not pinned by the fixed-commit benchmark input

- **Classification / prior class:** `INCORRECT`; `FIND-TASK-007-1` remains class-incomplete for the warm-measurement and API-call portion of AC-007.
- **Root cause / defect class:** The benchmark entrypoint pins only the cold snapshot's commit. It passes a mutable PR number to the first PR run and each warm run. `PrContext::pin` obtains the PR's *current* base, head, and paginated files independently on every invocation; it checks for movement within one invocation, not equality to the prior invocation or a caller-selected workload. The entrypoint shape permits a fixed cold tree with an unfixed PR workload.
- **Siblings:** `examples/live_pr.rs:117` first PR call and `:121` each warm call; Wyrd, VS Code, and Rust reports (`evidence/TASK-007/s20-wyrd-pr1.json`, `bench-vscode.json`, `bench-rust.json`) and their combined warm/API-call rows in TASK-007:89-95. Each report stores the observed base/head as output, but the recorded command supplies only `BCR_COMMIT` and `BCR_PR` as inputs.
- **Violated obligation:** AC-007 asks for *reproducible fixed-commit measurements* including warm p50/p95 and API calls, not only a fixed cold snapshot. R1 FIND-TASK-007-1 explicitly identified warm figures among the outputs that could not be reproduced after refs moved; its correction asks for rerunnable commands and all metrics.
- **Observable consequence:** After an open benchmark PR advances, the same documented command measures a different head tree, overlay, changed blobs, candidate fetches and PR-file pages while reporting the same cold commit. A change during the three warm calls can mix workloads in one percentile sample. The VS Code report already demonstrates the sensitivity: its pinned cold snapshot is complete, but the PR overlay is incomplete because that PR head is 2,678 changes behind current main. This is a source-path reproduction, not a claim that the recorded numbers themselves were wrong.
- **Testable correction:** Make the opt-in benchmark accept or otherwise enforce the recorded PR base/head workload for *each* first/warm call and fail visibly on drift; then capture runs whose workload can be rerun at those identities (or document a distinct, immutable benchmark fixture using the same production facades). Preserve ordinary `PrContext::run` semantics and source verification. A fake-provider check should move the PR between warm calls and prove the benchmark rejects or holds the fixed workload. The correction belongs at the benchmark input/proof boundary, not in snapshot persistence.

**Verification limits.** I inspected the immutable source and parsed the checked-in JSON reports with `jq`. I did not make credentialed GitHub calls or repeat the broad gate; the orchestrator is running that gate once. Existing tests prove cold-SHA pinning, but no focused proof in this candidate shows the PR workload stays fixed across the warm calls. The captured timings are observations under the named macOS environment, not assertions of identical wall-clock timing on rerun.

**Overall: FAIL** on AC-007's complete workload reproducibility; fixed cold-snapshot identity and the other reviewed capacity/provider evidence pass.
