## Findings

### TASK-A-1 — INCORRECT; prior FIND-TASK-005-4 class incomplete

**Defect class/root cause:** the scoped `PrContext::run` branch discards the head-tree listing's rejected count when it constructs `Ingest`; the warm branch carries it. The `Ingest` owner can represent `InvalidEntry` correctly, but the facade passes `0` for this sibling path. **Owner shape:** no new public shape is needed; carry the already available count through the shared coverage path.

**Obligation:** REQ-008's scoped omissions, REQ-009/010's incomplete overlay reporting, INV-002's distinguishable missing facts, and R1 FIND-4's requirement to retain rejected tree exclusions. **Evidence/reachable path:** a default-branch rejected tree entry makes cold build `Incomplete` and leaves no snapshot. On PR run, `snapshot=None`; if its head tree also contains a rejected entry, the scoped branch constructs `Ingest::new(&near, 0, ...)`. `Ingest::finish` therefore records no `InvalidEntry`, and `files.is_complete()` can set `overlay_complete=true` when all *accepted* nearby files are indexed. Scope still prevents `is_full()`, but the persisted context loses the cause of unknown head-tree coverage. Warm overlay passes `listing.rejected.len()` and is covered by the current test; cold/scoped is the sibling left open. **Consequence:** the caller sees scoped coverage without the rejected-entry exclusion or an incomplete overlay axis and cannot distinguish this missing head-tree fact from an ordinary bounded scope. **Correction/proof:** preserve rejected-entry coverage for both snapshot and scoped PR ingest; a fake provider test should first fail cold publication on a rejected default tree entry, then run a PR without a snapshot and assert its persisted context carries `InvalidEntry` and incomplete overlay while valid nearby context survives.

### TASK-A-2 — INCORRECT; rejected-file changed-path exclusion gap

**Defect class/root cause:** rejection of a PR-file record discards a usable canonical changed filename along with its invalid status/SHA/previous path, while the candidate exclusion set is built solely from validated `pinned.files`. **Owner shape:** `RejectedPath` retains only a raw filename/reason, so the rejection boundary does not preserve the validated path identity that downstream candidate filtering needs. **Sibling sites:** `near` also derives changed directories solely from `pinned.files`, so a rejected sole changed file cannot seed scoped neighbors; `diff_tokens` similarly omits its patch, though no trustworthy patch is required to be counted. The material failure is secondary selection of a known changed path.

**Obligation:** REQ-009 explicitly says a changed path is never selected again as secondary context; TASK-005 Scenario 2 repeats this. **Evidence/reachable path:** `validate_pull_request_file` validates a canonical filename before checking status and SHA; an invalid status or SHA thus can reject a record with a known changed path. `GitHubClient::pull_request_files` retains the raw filename in `RejectedPath`, and `pin` separates it from `pinned.files`. For a valid changed `src/handler.ts` referencing `src/user.ts`, with the PR listing's `src/user.ts` entry rejected for invalid SHA but its pinned head-tree entry valid, the index can rank `src/user.ts`; `changed` excludes only `pinned.files`, so `ranked.retain` keeps it. The current rejection test uses `src/other.ts`, which does not match the valid changed file's references. **Consequence:** a PR changed file can be published as secondary candidate context, consuming budget and violating diff/context separation. **Correction/proof:** preserve and use any independently validated rejected PR filename for changed-path exclusion and scoped-directory seeding without accepting invalid blob/status facts. A focused test should reject a canonical, rankable changed filename for bad status/SHA and assert it appears as `NotAnalyzed::Rejected` but never as a selected candidate; also show a valid sibling still yields context. Invalid filenames must remain untrusted.
