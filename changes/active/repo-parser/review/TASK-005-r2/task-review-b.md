## TASK-B-1 — INCORRECT: tree rejection loses eligibility information before completeness is decided

**Root cause and defect class.** `GitHubClient::tree` reduces every failed tree validation to `RejectedPath { path, reason }` (`github.rs:972–985`), and downstream ingestion treats that undifferentiated count as unknown coverage (`snapshot.rs:139–150,1015–1017`) or drops it in scoped mode (`pull_request.rs:179–190`). The rejected entry's independently validated mode/path/size facts are unavailable at the owner where eligibility is decided. This is a classification-before-coverage defect in candidate-owned data shape.

**Siblings and reachable paths.** (1) Cold build `ColdBuild::start → Ingest::new → finish → complete`: one rejected default-branch row makes `Coverage::unindexed` positive and prevents snapshot publication, even when its valid path and mode prove it excluded. A repository whose tree response repeatedly contains that row never obtains a reusable snapshot. (2) Incremental `Update::run` uses the same `ColdBuild::start/complete` path, so an otherwise complete update cannot advance its pointer. (3) Repository-scope PR overlays use the count and correctly lower full coverage when rejection might hide eligible source. (4) No-snapshot/scoped PR context explicitly passes zero rejected rows to `Ingest::new`, so its persisted `files.excluded[InvalidEntry]` and omission count lose a provider rejection, even when it may be an eligible neighbor. Scope remains `Scoped`, but the reason for missing facts is no longer distinguishable.

**Violated obligation and reproduction.** REQ-005 says an *unindexed eligible file* makes a cold attempt incomplete; REQ-006 permits publishing a complete validated snapshot. The spec's “Complete snapshot” definition covers every eligible file and counts excluded/unsupported paths separately. TASK-005-R1 FIND-4 explicitly qualifies rejected tree entries with “unless validated facts prove it ineligible” and requires retained excluded counts. INV-002 requires missing facts/skips to remain distinguishable. A tree response with a canonical `README.md`, valid file mode, and malformed SHA is rejected by `validate_tree_entry` before the known unsupported path can be classified. `Coverage::unindexed()` then counts it as missing eligible source, yielding `Incomplete(UnindexedFiles)` and no pointer despite all actual eligible files being indexed. Conversely, with no snapshot, a rejected canonical `src/neighbor.ts` row is omitted from the scoped `Ingest::new` call entirely. The tests at `snapshot.rs:2310–2345` and `pull_request.rs:1121–1159` cover only unknown `.ts` cases and do not disprove either sibling.

**Correction and focused proof.** At the GitHub tree validation/eligibility handoff, preserve enough raw entry facts to distinguish a provably excluded rejected row from a possibly eligible rejected row. Reuse shared eligibility rules for validated path/mode/size facts; do not assume unknown mode or invalid path is excluded. Count only the latter against completeness and keep rejection diagnostics/exclusion counts in both repository and scoped context. Prove a default-branch tree containing one rejected but provably unsupported row still publishes a complete snapshot, while an ambiguous rejected row remains incomplete; prove a scoped PR preserves an ambiguous rejected-tree count/reason while still returning valid-file context. No new trait, dependency, or product behavior is needed.

Overall: **FAIL**. The prior FIND-TASK-005-4 correction is incomplete at its tree-rejection classification boundary; FIND-1–3 close on the inspected paths. Verification limit: this is a traced source-path review; I did not run the full gate independently.
