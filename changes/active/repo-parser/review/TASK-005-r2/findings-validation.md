## Blocking ledger

### FIND-TASK-005-4 — Rejected tree entries are not classified before completeness (`CLASS_INCOMPLETE`)

- **Claims:** TASK-B-1, DOMAIN-DUR-1, and the tree portion of TASK-A-1. **Gate:** task contract, REQ-005, REQ-006, REQ-009, INV-002; also the R1 correction's explicit exception for entries proved ineligible. **Classification:** INCORRECT/DRIFT. **Defect class/root cause:** the R1 fix converted every provider rejection into an unindexed eligible file by counting `Coverage.excluded[InvalidEntry]` in `Coverage::unindexed` (`snapshot.rs:130-150`). `RejectedPath` stores only raw path and reason (`github.rs:462-469`), and `Ingest::new` accepts only a rejection count (`snapshot.rs:778-813`), so the shared owner has discarded the facts needed to distinguish known ineligible paths from unknown eligibility.
- **Reachability and siblings:** `GitHubClient::tree` validates path, then mode, then SHA (`github.rs:967-982,1382-1404`). A canonical `README.md` with an invalid SHA is rejected although the symbolic path query proves it unsupported (`eligibility.rs:264-280`); likewise a canonical unsupported path with an unknown mode cannot be an eligible source under the spec. `ColdBuild::start` passes the count to `Ingest::new`, and `ColdBuild::complete` refuses publication whenever `unindexed` is nonzero (`snapshot.rs:574-598,637-681`). `Update::run` uses the same `start` and `complete` path (`update.rs:70-102`), so an update also cannot advance its pointer. Repository-scope `PrContext::run` uses `Ingest::new` and `files.is_complete()` for overlay coverage (`pull_request.rs:164-173,220-230`). Scoped `PrContext::run` instead passes zero and omits the rejected entry from `near` (`pull_request.rs:175-190,541-552`): a rejected canonical nearby path is absent from scoped exclusion/omission counts even though the result is already marked scoped. These are one rejected-entry classification problem, with cold build, update, repository overlay, and scoped diagnostics as sibling effects.
- **Reproduction/consequence:** For a default tree containing one valid eligible source and one invalid-SHA `README.md`, the source is indexed, but `InvalidEntry=1`, `unindexed=1`, and `ColdBuildOutcome::Incomplete(UnindexedFiles { count: 1 })` follow deterministically. Repeating the build at the same tree cannot create a snapshot. This exceeds the approved definition of a complete snapshot: every **eligible** file indexed, with unsupported/excluded paths counted separately (`spec.md:31-33,62-63`). For a rejected supported path whose mode or SHA prevents classification, incomplete coverage remains correct; the correction must retain that protection. The current cold-build test explicitly asserts every rejection makes publication impossible (`snapshot.rs:2307-2345`), so it does not prove the required distinction.
- **Decision-complete correction:** At the shared provider-to-eligibility boundary, preserve the validated path and any trusted mode facts for rejected entries. Classify a rejection as an exclusion only where those facts *prove* ineligibility under the existing path/attribute rules; keep genuinely unknown or potentially eligible entries incomplete. Carry this distinction into shared `Coverage`, so cold publication and updates use the same truth, and scoped coverage retains nearby rejected-entry diagnostics without claiming repository coverage. Reuse `RelativePath` validation and the existing eligibility query/classifier; do not add a second eligibility policy or relax validation of source bytes and Git identities. **Closure proof:** focused fake-provider cold and update paths with invalid SHA on a canonical unsupported path publish a complete snapshot/update; an invalid supported path or unknown eligibility remains incomplete and leaves the pointer unchanged; repository PR overlay and nearby scoped PR context reflect the same classification, while valid source still ranks. Recheck the existing unknown-mode rejection case.

### FIND-TASK-005-5 — Rejected PR files escape changed-path exclusion (`CONFIRMED`)

- **Claim:** TASK-A-2. **Gate:** production path and task contract, REQ-003 and REQ-009 (`spec.md:57,69`). **Classification:** INCORRECT. **Defect class/root cause:** `GitHubClient::pull_request_files` returns rejected records with their raw filename (`github.rs:1141-1157`), but `PrContext::run` builds the secondary-candidate exclusion set only from accepted `pinned.files` (`pull_request.rs:234-236`). The rejected entry's canonical changed-path identity is lost to this rule when its status, SHA, or previous path is invalid.
- **Reachability and siblings:** A PR-files response can contain `src/user.ts` with a canonical filename and invalid SHA plus a valid changed `src/handler.ts` whose added line references `lookupUser`. The head tree can still contain verified `src/user.ts`, so snapshot reuse or overlay ingest supplies its declaration. `rank` can return that path; `ranked.retain` sees no accepted PR-file path for it; `pack` fetches its verified head-tree blob and includes it as secondary context (`pull_request.rs:220-253,407-459,463-495`). The same accepted-only set seeds `near` in the scoped fallback (`pull_request.rs:175-190`); this is a related loss of changed-path identity, although the blocking observable effect is selected secondary context. A rejected PR entry is correctly recorded in `not_analyzed` and `pr_files_rejected`, but those fields do not prevent the selection.
- **Reproduction/consequence:** The traced input returns a selected span from `src/user.ts`, a path that the PR-files endpoint identified as changed. This directly violates “a changed path is never selected again as secondary context,” independent of `is_full()` being false. The existing rejected-PR test uses an unrelated `src/other.ts` and therefore cannot detect this (`pull_request.rs:1087-1119`).
- **Decision-complete correction:** Preserve the canonical filename, when independently valid, as a changed path even if other PR-file fields fail validation. Exclude the union of accepted and canonically identifiable rejected changed paths before secondary packing, using the existing `RelativePath` boundary; never trust an invalid filename as an identity. Carry that same set into any scoped-neighbor decision that claims to be based on changed paths. Keep the rejected diagnostic and partial PR coverage. **Closure proof:** a focused public PR-facade test with a canonical rejected changed path containing a matching declaration and another valid changed file must rank other candidates but never select the rejected changed path; an invalid filename stays diagnostic only, and accepted changed paths remain excluded.
