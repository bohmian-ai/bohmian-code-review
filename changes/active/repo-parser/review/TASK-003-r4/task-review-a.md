## Proposed findings

### TASK-A-1 — INCORRECT: verified archive files accumulate until the compressed chunk ends

- **Root cause and defect class:** The tar sink appends each completed file to an unbounded `verified` vector; `consume_archive` drains it only after `GzDecoder::write_all` finishes an entire provider chunk. The queue's shape permits source-set accumulation. Sibling locations: `TarStream::finish_entry` producer (`archive.rs:215-219`), `TarStream::write` decompression sink (`archive.rs:233-239`), and `Ingest::consume_archive` chunk-level drain (`snapshot.rs:681-692`). No other source-bearing queue was found in this task's archive path.
- **Violated obligation:** REQ-005 streams the archive without retaining the full source set; REQ-013 bounds memory; TASK-003 Scenario 1 requires a streamed source-free snapshot. The code documentation itself says one wanted file is held (`archive.rs:3-8`, `snapshot.rs:667-673`).
- **Reachable consequence:** `HttpBody::chunk` is not constrained to contain one tar entry. A provider chunk containing many compressed entries makes `write_all` decompress and queue all verified file bytes before any is indexed or freed. A highly compressible archive can therefore hold most eligible source files simultaneously, up to the 4 GiB expansion ceiling, even though each file obeys the 1 MiB bound. This defeats the memory and source-lifetime contract; current tests use small archives and do not assert peak buffered bytes.
- **Testable correction:** Transfer each verified file to `Ingest` as soon as it completes, or otherwise enforce a fixed small bound on the handoff while preserving async chunk consumption and verification. A focused test should feed one compressed chunk containing many eligible files and show peak retained raw file bytes is bounded independently of file count, while the snapshot contains all facts.

### TASK-A-2 — INCORRECT: collection acts on a stale unreferenced list after a record is re-touched

- **Root cause and defect class:** `Snapshots::collect` treats `unreferenced`'s returned key list as a durable claim. The snapshot store contract returns only keys; there is no ownership or atomic conditional deletion protecting the `touched_at` and pointer predicates through object and record deletion. Sibling locations: the `SnapshotStore::unreferenced` contract (`persistence.rs:183-196`), in-memory implementation (`testing.rs:280-300`), `Snapshots::collect` (`snapshot.rs:289-303`), and `ColdBuild::publish` re-touch/create/read/pointer path (`snapshot.rs:582-607`). `remove_repository` calls `collect` only after pointer removal and is not a separate sibling when its documented no-active-build precondition holds.
- **Violated obligation:** REQ-006 and TASK-003 Scenario 4 / acceptance criterion explicitly say collection never collects a record re-touched since `older_than`.
- **Reachable consequence:** Start with an old unreferenced object and record. Collector obtains the key, then a cold build upserts its record and adopts the byte-identical object. Collector can delete that newly re-touched object's bytes and record before the build's compare-and-swap. The build may publish a pointer to the now missing object. Even when the build does not publish, a re-touched record was collected. The existing test re-touches before listing and cannot exercise this interleaving.
- **Testable correction:** Make the stale/unreferenced eligibility and deletion claim survive concurrent record re-touch and pointer publication; ensure a late collector cannot delete an object that a build has re-touched or is about to publish. Exercise the listed interleaving with deterministic stalls, and assert the re-touched record and any published object remain present. The correction belongs at the snapshot store/collection seam, not at one caller.

## Archive dependency judgment

The hand-written `TarStream` is warranted under revision 12's constraints. The installed `tar` crate is pull-based over `std::io::Read`; feeding it asynchronously streamed HTTP bytes without whole-archive buffering needs a blocking bridge or another async dependency and complicates drop ownership. `flate2::write::GzDecoder` is already installed and supplies the push side. This judgment accepts a bounded streaming parser, not the current unbounded verified-file handoff (TASK-A-1).

Overall: **FAIL**. The exact focused collection test passed; it does not cover its identified race. The prior r1–r3 synchronous deadline/cancellation defects were superseded by the drop-future contract. Prior record-before-object, invalid-tree-entry coverage, and attribute reset classes were rechecked in current source.
