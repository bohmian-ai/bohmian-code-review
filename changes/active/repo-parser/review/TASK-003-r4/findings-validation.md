## Deduplicated blocking ledger

### FIND-TASK-003-8 — CONFIRMED

- **Sources:** `TASK-A-1`, `DOM-TRUST-R4-1`, `BUDGET-1`. **Gate:** task contract, spec REQ-005 and REQ-013; TASK-003 Scenario 1. **Classification:** `INCORRECT`. **Defect class:** verified source bytes accumulate in the tar-to-ingest handoff until a whole compressed chunk has been decompressed.
- **Root cause and siblings:** `TarStream::finish_entry` pushes every verified file and retains its bytes in `verified` (`archive.rs:215-218`). `Ingest::consume_archive` calls `decoder.write_all(&chunk)` before draining that vector (`snapshot.rs:681-692`). One provider chunk can contain many eligible files; the entire source set in that chunk remains in memory, up to the expanded-archive bound. The sole sibling is the same archive handoff; fallback ingests each returned blob directly.
- **Independent reproduction:** Public `ColdBuild::run` calls `consume_archive` (`snapshot.rs:517-521`). A valid gzip response containing many small, wanted files in one body chunk makes `write_all` finish all entries; `finish_entry` queues all verified `Vec<u8>` values before `ingest_verified` runs. The default expanded ceiling is 4 GiB (`snapshot.rs:45-58`), so the queue is not a one-file bound. This follows from the complete producer and consumer bodies and requires no new input kind.
- **Consequence:** A cold build can retain almost the whole eligible source set at once, contrary to streaming ingest and the memory bound. **Correction boundary:** make the existing `TarStream`/`Ingest` handoff release or ingest each verified file while processing the chunk, or otherwise cap feed work so only one verified file can wait for indexing. Preserve blob verification before indexing, bounded PAX metadata, path eligibility, gzip and expansion bounds, and archive error handling. No new queue, worker, or dependency is needed. **Closure proof:** one public cold-build test supplies one compressed body chunk containing several wanted files and observes a bounded maximum of simultaneously retained verified source bytes while all files index correctly; run the existing archive owner tests.

### FIND-TASK-003-9 — CONFIRMED

- **Sources:** `TASK-A-2`, `TASK-B-1`, `CONC-1`. **Gate:** task contract, spec REQ-006 and REQ-013, TASK-003 Scenario 4; absolute durability boundary. **Classification:** `INCORRECT`. **Defect class:** collection treats a stale list of eligible record keys as a durable deletion claim.
- **Root cause and siblings:** `Snapshots::collect` lists unreferenced old keys, then awaits object deletion and unconditionally removes their records (`snapshot.rs:289-303`). The injected store's `unreferenced` filters once (`testing.rs:275-300`) and `delete_record` deletes without rechecking touch time or pointer (`testing.rs:308-316`). A concurrent `ColdBuild::publish` refreshes that same deterministic key, creates or validates the object, and advances its pointer (`snapshot.rs:578-609`). `remove_repository` invokes `collect` only under its documented no-active-build caller rule (`snapshot.rs:306-315`); that distinct operation is not a second defect under its precondition.
- **Independent reproduction:** Start with an old, unreferenced record for the same tree key. Let `collect(identity, older_than)` receive the key from `unreferenced`, pause before `storage.delete`, then let a new build refresh the record. Resume collection through object and record deletion. The new build can subsequently CAS a pointer to the missing object, or collection can delete an object after CAS. The caller's cutoff being older than maximum build duration does not prevent selection of an old record just before refresh. This interleaving is admitted by the public facade and the store contract (`persistence.rs:176-215`).
- **Consequence:** Cleanup can erase a live or newly published object, break pointer validity, and leave an unrecorded object state. **Correction boundary:** make the candidate-owned `SnapshotStore` collection eligibility a durable claim coordinated atomically with record refresh and pointer publication; `Snapshots::collect` may delete only a successfully claimed key, and a build racing a claim must retry or fail its publication without pointing at an object being deleted. Preserve record-before-object order, idempotent retry, pointer CAS, the caller-supplied cutoff, and identity isolation. A second read of `unreferenced` alone is insufficient because the race simply moves after it. This is an internal persistence-seam correction to deliver the already approved concurrency and durability behavior, not a new product decision. **Closure proof:** deterministic paused-store tests for both orderings (collector claims first; builder refreshes/publishes first), asserting no pointer names a missing object, every object has a record, cutoff still protects recently touched records, and a retry converges.

### FIND-TASK-003-10 — CONFIRMED

- **Source:** `BUDGET-2`. **Gate:** task contract, spec REQ-005, INV-002 and INV-003; absolute source-trust boundary. **Classification:** `INCORRECT`. **Defect class:** a provider transfer ceiling is mistaken for verified file oversize.
- **Root cause and siblings:** `GitHubClient::blob` rejects bodies over `RequestLimits.max_blob_bytes` before hashing (`github.rs:994-1017`); `Ingest::fallback` maps every `ResponseTooLarge` to benign `SkipReason::Oversize` (`snapshot.rs:704-727`), and `Coverage::is_complete` accepts benign skips (`snapshot.rs:126-130`). This is the sole blob fallback mapping; the successful-byte branch compares against `max_file_bytes` correctly.
- **Independent reproduction:** Configure `RequestLimits.max_blob_bytes` below `ColdBuildLimits.max_file_bytes`, supply an eligible file between those sizes, and omit it from the archive. The public build reaches fallback, the provider stops before returning or verifying the blob, the path becomes benign `Oversize`, and a complete snapshot can publish. Both limits are independently configurable and no constructor rejects this relationship (`github.rs:202-232`, `snapshot.rs:41-59`).
- **Consequence:** The snapshot silently treats unverified eligible source as deliberately excluded, losing facts and claiming complete coverage. **Correction boundary:** at the existing fallback owner, count `ResponseTooLarge` as benign oversize only when its reported limit is at least the eligible file ceiling; otherwise record an incomplete fetch/budget reason. Preserve genuinely verified oversize and LFS skips. No new provider API is needed because the error already carries `limit`. **Closure proof:** focused public build with provider ceiling below file ceiling and an omitted eligible file returns incomplete without moving the pointer; equal or greater ceiling still permits a genuine oversize skip.

### FIND-TASK-003-11 — CONFIRMED

- **Source:** `BUDGET-3`. **Gate:** task contract, spec REQ-005 and REQ-013, TASK-003 Scenario 2. **Classification:** `INCORRECT`. **Defect class:** archive-bound exhaustion is stored only as a diagnostic, outside the publication decision.
- **Root cause and siblings:** `consume_archive` stores a gzip/tar/expansion error in `IngestStats.archive_error` (`snapshot.rs:681-693`); `ColdBuild::run` falls back and publishes whenever coverage is complete (`snapshot.rs:517-552`). The compressed archive bound and expanded archive bound both enter this path; neither is a publication veto. The existing owner test explicitly expects `Published` after expansion exhaustion when fallback fetches all files (`snapshot.rs:1303-1327`).
- **Independent reproduction:** That existing test supplies an archive expansion ceiling of 64 bytes; it asserts the `archive expansion` error, then asserts complete coverage and `Published`. The public cold-build path therefore violates the task's explicit rule that an exhausted archive bound leaves the pointer unmoved and returns incomplete coverage plus a scoped-fallback reason, even when blob fallback succeeds.
- **Consequence:** The cold build advances the pointer after a stated exhaustion condition and masks the reason the PR-context facade needs for scoped fallback. **Correction boundary:** carry archive-bound exhaustion from the existing ingest result into `ColdBuild::run`'s incomplete decision, preserving per-file fallback accounting and exact coverage, and leave the pointer unchanged. Ordinary archive omission/substitution that verified fallback can repair remains distinct. **Closure proof:** change the focused exhaustion test to assert incomplete outcome and prior pointer for both compressed and expanded bounds, including when fallback retrieves all listed files; run the cold-build owner lane.

## Ponytail assessment of the tar reader

`tar 0.4` is already in the workspace lockfile and this crate's dev dependencies, but its entry iterator pulls from a synchronous `Read`. The production GitHub archive is an async chunk stream, and the approved design drops a future for cancellation with no detached blocking worker. Replacing `TarStream` with `tar::Archive` would require a blocking bridge, a worker/channel, or buffering the archive; none is a smaller safe use of the existing dependency. A bounded push parser is therefore warranted for this execution model. Its roughly 435 lines still need the per-entry handoff correction in FIND-8; this judgment does not excuse an unbounded verified queue. The `tar` dependency remains useful for test fixture generation.
