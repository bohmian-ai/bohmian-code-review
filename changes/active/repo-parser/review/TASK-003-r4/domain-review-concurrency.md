## Result: FAIL

### CONC-1 — A selected cleanup key is not protected against a concurrent build

**Classification:** INCORRECT. **Defect class:** the cleanup selection is a detached list of bare keys, while `delete_record` is unconditional; neither operation reserves the key against a later `upsert_record`. The candidate-owned `SnapshotStore` contract permits this race. **Owner shape:** `unreferenced` returning `Vec<ObjectKey>` and a blind `delete_record` allow the decision that a key is stale to expire before its object is deleted.

**Root cause and siblings:** `Snapshots::collect` obtains `unreferenced(identity, older_than)` once, then awaits `storage.delete` and `store.delete_record` for each key. In parallel, `ColdBuild::publish` re-touches the same deterministic key before creating/adopting its object and swapping the pointer. `remove_repository` routes through the same `collect` sink after dropping pointers; its documented no-active-build assumption does not close the ordinary `collect` race. The in-memory store implements the unsafe contract directly: `unreferenced` filters under locks and returns keys; `upsert_record` may update one afterwards; `delete_record` removes it without a touched-time or pointer condition.

**Reachable schedule:** Start with an old unreferenced record for key K. Collector selects K. A new cold build for K upserts its record, so its `touched_at` is newer than `older_than`. Collector resumes and deletes K's object and record. The build creates K's object, then its pointer compare-and-swap succeeds. The pointer now names an object with no record. In another ordering, the build validates an existing K object, collector deletes it, and the pointer moves to a missing object. Both violate REQ-006, REQ-012, REQ-013 and TASK-003 Scenario 4 even when the caller chooses `older_than` beyond the build timeout; the selection predates the re-touch. A drop or retry cannot make the intermediate published pointer valid.

**Verification:** Source trace above is sufficient to reproduce the interleaving at the public facades. The current `collect_removes_only_stale_unreferenced_records` test re-touches K *before* calling `collect`, so it does not exercise selection followed by re-touch. No concurrent collect/build test is present. I did not modify or run the candidate.

**Testable correction:** Make the snapshot-store cleanup/publication contract coordinate the lifetime of a selected key through object deletion. A build re-touch must invalidate or wait for a cleanup claim before it creates/adopts the object; cleanup must not delete a key that has been re-touched or pointed to after selection. Keep record-before-object and object-before-record order. Prove the two schedules above using a stalled object delete and concurrent `ColdBuild::run`, then assert the final pointer reads and every stored object has a record. Apply the same rule to namespace removal if builds can overlap it, or make that precondition explicit at its public boundary.

## Other boundary checks and limits

The isolated drop tests cover record-upsert, object-create, and pre-CAS stalls, with and without a prior pointer. `MemoryStorage::create` is atomic and create-only; existing bytes are compared before pointer publication. The pointer key is checked against the caller identity before object reads, and collected keys are namespace checked before deletes. The in-memory store scopes pointers and records by identity. These checks cover sequential cancellation and isolation, not the reported cross-facade interleaving. No concrete SQL or object-store adapter is in this task, so its transactional semantics cannot be assessed here.
