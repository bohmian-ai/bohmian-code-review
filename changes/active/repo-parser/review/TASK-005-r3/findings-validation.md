### FIND-TASK-005-6 — Changed-head ingest bypasses the scoped file ceiling (`CONFIRMED`)

- **Claims:** TASK-B-2, BUDGET-1. **Gate:** task contract REQ-008/013 and TASK-005 scoped fallback. **Classification:** INCORRECT. **Defect class/root cause:** scoped capacity is calculated only after all accepted changed heads have been fetched and, when pending, ingested. `PrContext::run` calls `changed_head` for every accepted PR file (`pull_request.rs:210-224`); `changed_head` calls `ingest.ingest` without a scoped capacity check (`pull_request.rs:375-415`). `max_scoped_files.saturating_sub(ingest.indexed())` bounds only the later fallback, so the candidate-owned PR admission flow allows already-indexed changed heads to exceed the advertised file ceiling.
- **Reachability and siblings:** With no compatible snapshot, `near` includes accepted changed paths in the same directory, and `Ingest::new` makes them pending (`pull_request.rs:181-194`; `snapshot.rs:784-814`). Each valid changed patch with a matching head-tree SHA and blob is fetched and ingested before fallback. A PR with two such files and `max_scoped_files = 1` finishes with `coverage.files.indexed >= 2`; the same pattern scales to the PR-file ceiling. Siblings are every accepted changed head, indexed count, provider blob work associated with scoped indexing, and subsequent `NotFetched` omissions. The existing `scoped_bound_skips_excluded_neighbors` test has only one changed head and does not exercise this path.
- **Correction boundary:** Enforce the scoped *index* ceiling at the PR-to-`Ingest` admission point across changed-head and fallback ingestion, while continuing to verify, fetch and analyze valid changed heads for their own diff/ranking obligations under REQ-009/010. Do not cap changed-file analysis at `max_scoped_files`, erase file-local failure reporting, or turn a scoped result into full coverage. Reuse `Ingest::indexed` and existing `NotFetched` coverage; keep repository-scope overlay behavior separate. **Closure proof:** with two or more valid changed heads, no snapshot, and a one-file scoped ceiling, both changed files contribute analysis or explicit file-local failure, `indexed <= 1`, eligible unindexed paths are reported, and bounded fallback does not fetch another index candidate. Check the positive one-head path and warm overlay as controls.

### FIND-TASK-005-7 — Expiry cleanup can retire a publication before its object write finishes (`REVISED`)

- **Claim:** DOMAIN-DUR-1. **Gate:** absolute durability and task contract REQ-012/013/014/015, INV-005, TASK-005 Scenario 3. **Classification:** INCORRECT. **Defect class/root cause:** `Contexts::publish` makes its record expiry-eligible before awaiting object creation (`context.rs:316-338`). `ContextStore::expired_contexts` selects records solely by `expires_at` (`persistence.rs:266-275`), and `Contexts::collect_expired` deletes the object and record without coordinating with an in-flight publication (`context.rs:407-431`). The context store is candidate-owned; its current read/list/delete shape allows cleanup to erase a publication's only record before the source object is created.
- **Reachability and siblings:** `PrContext::run` calls `Contexts::publish` (`pull_request.rs:293-300`); `Contexts::collect_expired` is a public independent facade. The test store lists records whose `expires_at <= now` and removes by `(identity,id)` (`testing.rs:403-469`), so the following interleaving is supported by its contract: publication upserts a record; its object create remains pending until or beyond `expires_at`; cleanup lists that record, sees no object, and deletes the record; object create completes. Publication now returns an ID that `read` rejects, and storage holds source text with no record. If create completes just before cleanup's delete, publication may instead return a soon-unreadable ID. These are one lifecycle race across success, exact-key read, object deletion, and metadata deletion. Distinct per-publication IDs (R1 FIND-2) do not prevent cleanup from racing the *same* publication.
- **Reproduction/consequence:** The source trace uses a paused or delayed object-store create and cleanup at the recorded expiry. The library imposes no invocation maximum (`spec.md:75-77`), so the caller-supplied bound need not be less than 24 hours. This is a rare scheduling path, but the object-without-record outcome violates the explicit absolute durability rule that every written object remains recorded. Existing dropped-publication and expiry tests stall upsert/create or collection separately; none advances time past one publication's expiry while create is in flight.
- **Correction boundary:** Keep the record-before-object and object-before-record orders and the exact 24-hour *read* cutoff. At the candidate-owned context cleanup/store boundary, let the caller supply a collection cutoff/grace longer than its publication timeout, as snapshot collection already requires (`spec.md:63`; `snapshot.rs:311-317`). Collect only records whose `expires_at` is past that safe cutoff. This separates authorization expiry from safe physical deletion without a library-imposed invocation maximum, new backend, or transaction across object IO. Preserve the existing object-then-record delete order, missing-object success, lag reporting, and retry behavior. The caller's cutoff obligation must be part of the context-store/facade contract. **Closure proof:** pause a context object create through its read expiry, sweep at the read cutoff with an allowed grace and prove its metadata remains; release create and prove publication does not leave an unrecorded object. Drop another publication after record upsert, sweep after the caller's timeout plus grace, and prove cleanup removes its absent-object record. Verify reads fail at `expires_at` in both cases and ordinary expired contexts are eventually collected.
