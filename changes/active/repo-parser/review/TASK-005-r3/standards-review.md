## Material finding

### STANDARDS-1 — A rejected root policy file is classified as a benign source exclusion

- **Classification:** VIOLATION. **Defect class:** provider rejection loses the root eligibility-policy role before coverage classification. The shared classification owner permits it; its `path_exclusion` result treats every unsupported path as safely ineligible even when the path is `.gitattributes`.
- **Written rules:** `AGENTS.md:23` says the outer pipeline owns repository eligibility and must never report partial caller-supplied indexes as complete repository coverage. `architecture/agent-rules.md:7` says an omitted file must not become apparent success. Root `.gitattributes` overrides are required by `changes/active/repo-parser/spec.md` REQ-005's eligibility definition and are implemented by the existing `RootAttributes` owner; the standards violation is the false completeness claim.
- **Source path reproduction:** A Git tree has valid `src/a.ts` and a root `.gitattributes` row with canonical path but invalid blob SHA. `GitHubClient::tree` rejects the row, leaving it in `listing.rejected`. `root_attributes` searches only accepted `entries` and returns defaults. `classify` passes the rejected canonical `.gitattributes` path through `path_exclusion`, which returns `Unsupported`, so `unknown` remains zero. The ingest coverage has no `InvalidEntry`; `Coverage::is_complete()` returns true if the source blob indexed. With a root rule such as `src/* linguist-generated`, the candidate can index and publish files the actual tree policy excludes while claiming complete coverage. No current test covers a rejected `.gitattributes` row.
- **Sibling paths and effects:** `ColdBuild::start` uses this classification and `ColdBuild::complete` can publish a complete snapshot and pointer. `Update::run` calls the same `cold.start` and `cold.complete`, so it can advance the pointer on the wrong eligibility set. `PrContext::run` calls the same `root_attributes` for the head tree: a warm repository overlay can set `overlay_complete` and `is_full()` true; its scoped branch stays `Scope::Scoped` but still omits the global root-policy rejection from nearby-only diagnostics and may rank wrong nearby files. These are one finding at the shared provider-to-eligibility boundary.
- **Testable correction:** Preserve the rejected root `.gitattributes` fact as unknown eligibility policy before applying path-only benign exclusion. Reuse the existing root-attribute and coverage owners so cold/update publication is incomplete, a warm overlay cannot claim full coverage, and a scoped result retains the global rejection diagnostic while remaining scoped. Prove the four sibling paths with a fake-provider invalid-SHA root `.gitattributes` alongside a rule-sensitive eligible source, and retain the positive case where ordinary unsupported rejected files are benign.
