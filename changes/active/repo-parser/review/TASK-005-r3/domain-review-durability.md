## Proposed finding

**DOMAIN-DUR-1 — INCORRECT; expiry collection can retire an in-flight context publication.** The root cause is that the context record is made cleanup-eligible at `now + 24h` before its object write has completed, while `ContextStore::expired_contexts` lists it without a claim or other exclusion of active publications. The owner's candidate-owned trait shape permits unconditional deletion after selection. This differs from the snapshot store's explicit claim/upsert exclusion, and context cleanup has no `older_than > build timeout` precondition. The approved spec gives the library no invocation maximum (`spec.md:75–77,95`); a caller supplies a timeout and may keep a future live across the cutoff.

Reachable interleaving from `PrContext::run`: `Contexts::publish` upserts the record (`context.rs:326`), then awaits `ObjectStorage::create` (`context.rs:327`). If the object create remains pending until `expires_at`, a concurrent `collect_expired` lists and removes that record (`context.rs:413–425`). When create finishes, `publish` returns `Ok(record)` (`context.rs:338`) and the public facade returns an ID (`pull_request.rs:293–300`) for an object with no record. `Contexts::read` then returns `NotFound` at its exact metadata lookup (`context.rs:361–366`); no future expiry sweep can discover the unrecorded source object. If create wrote bytes before pausing, the sweep deletes object and record and the resumed publication still reports success. These are sibling outcomes of the same missing in-flight publication/collection coordination: publication success, exact-key read failure, and cleanup losing its source-bearing object target. The existing dropped-call and independent-expiry tests pause one side or use different IDs; neither resumes a publication after cleanup of its own ID.

This violates TASK-005 Scenario 3's no-unrecorded-object and readable-retry contract, REQ-012/013's valid durable state after interruption, and REQ-014/INV-005's bounded source retention. It is a durability boundary even though a correctly chosen short consumer timeout makes the race uncommon. The correction belongs at the context publication/collection record boundary: ensure an in-flight publication cannot finish successfully after collection has retired its record, and ensure every completed object remains recorded or is removed. Preserve record-before-object creation, object-before-record deletion, exact-key reads, separate publication lifetimes, and failed-delete lag reporting. A focused paused-clock interleaving should hold the object create after record upsert, advance to expiry, collect that same ID, then resume publication and assert either a readable valid publication or explicit failure with no unrecorded object; cover the already-written-object pause as the sibling.
