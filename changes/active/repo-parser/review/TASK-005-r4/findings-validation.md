## Blocking ledger

### FIND-TASK-005-8 — Actual PR blob bytes bypass the file limit

- **Source/status/gate:** TASK-A-1; **CONFIRMED**. Task contract REQ-004/013 and the eligible-file definition in `spec.md` (at most 1 MiB initially), plus the public `PrContextLimits::max_file_bytes` contract (`pull_request.rs:58`). **Classification:** INCORRECT/VIOLATION. **Root cause/defect class:** PR source admission trusts optional tree size, then consumes verified blob bytes without checking actual length against the PR file limit. The provider's independent `max_blob_bytes` is a transport ceiling, not this eligibility ceiling.
- **Siblings and trace:** `PrContext::run` obtains the tree, calls `root_attributes`, and constructs `Ingest::new` with its file limit (`pull_request.rs:155-195`). `eligibility::exclusion` excludes oversize only when `entry.size` is `Some` (`eligibility.rs:267-281`); a valid file/executable entry with `size: None` remains eligible. Each valid PR file reaches `changed_head`, whose `client.blob` returns SHA-verified bytes and whose pending branch indexes them (`pull_request.rs:396-428`) without a length check. `Ingest::reuse` can also load facts from a compatible prior snapshot for the same blob when current size is absent (`snapshot.rs:910-934`), with no current PR-bound check; this is the warm sibling. After ranking, `PrContext::pack` fetches selected candidate bytes and passes them to `build_candidate_context` (`pull_request.rs:441-487`) without a length check; this is the source-bearing output sibling. The cold/update `Ingest::fallback` already checks actual bytes (`snapshot.rs:938-965`), proving transport and eligibility limits are distinct.
- **Reproduction/consequence:** Supply an otherwise valid pinned PR/head tree whose `src/handler.ts` and matching candidate `src/user.ts` have `size: None`, verified blobs each larger than the configured PR file bound but below `GitHubClient`'s blob ceiling, and a valid patch referencing the candidate. The first enters changed-head analysis and, when pending, the index. The second can be fetched and packed into the published context. A warm snapshot can supply the candidate fact before packing. This violates file admission and lets an oversized candidate occupy the context object; the ranking and selected spans can differ from a size-compliant run. Source trace reproduces the branch deterministically; no candidate code was changed for a test.
- **Smallest correction:** Enforce actual-byte eligibility at the shared PR source admission boundary for changed heads and selected candidate fetches, and prevent reuse of facts that cannot be proved within the current PR limit. Reuse `PrContextLimits::max_file_bytes`, `Ingest`'s existing oversize/skip and per-file not-analyzed mechanisms, and keep mandatory analysis of other valid changed heads, SHA verification, selected-candidate-only fetch, and honest coverage. The implementation may choose the smallest shared owner, but one guard only on changed heads or only on packing leaves a sibling open. **Closure proof:** a focused public PR-facade test with absent tree sizes and blobs on both sides of the configured limit verifies every oversize changed/candidate sibling is excluded or diagnosed, valid files still rank and pack, and warm reuse cannot reintroduce the oversized fact. Check `max_blob_bytes` larger than the PR limit to isolate this rule.

### FIND-TASK-005-9 — Executable root attributes are ignored

- **Source/status/gate:** DOMAIN-TRUST-1; **CONFIRMED**. Task contract: eligible files include modes `100644` and `100755` and root `.gitattributes` overrides generated/vendored eligibility (`spec.md`, Terms); complete snapshot/overlay claims in REQ-005/006/009. **Classification:** INCORRECT. **Root cause/defect class:** shared root-policy loader accepts `TreeEntryMode::File` alone although provider validation and eligibility accept `TreeEntryMode::Executable` as a valid blob mode (`snapshot.rs:746`, `eligibility.rs:267-281`). This is an overly narrow mode check at the policy producer.
- **Siblings and trace:** `root_attributes` defaults policy when no regular-mode `.gitattributes` entry exists (`snapshot.rs:739-752`). Cold `ColdBuild::start` (`snapshot.rs:574-589`) and update through the same start path, plus `PrContext::run` for warm overlay and scoped fallback (`pull_request.rs:155-195`), all use that shared loader. Each then calls the same `classify`, so all four paths can admit generated/vendored files under defaults and report complete eligibility/index coverage. The `.gitattributes` executable entry itself is excluded as unsupported symbolic source; that does not erase its role as policy input.
- **Reproduction/consequence:** Put a valid, SHA-verified root `.gitattributes` at mode `100755` with `generated/* linguist-generated`, and a valid source under `generated/`. The loader chooses `RootAttributes::default()` despite the policy blob being available; `classify` admits and indexes the generated source. Cold publication/update can advance a supposedly complete pointer, and PR overlay/scoped context can rank or pack a file the repository policy excludes. This is a deterministic source-path reproduction.
- **Smallest correction:** In the existing `root_attributes` owner, accept both admitted blob modes for the root policy; reuse the current fetch and parser, with no new policy type or separate caller checks. Preserve errors on failed policy fetch/verification and the maintainer decision for malformed modes/SHAs and noncanonical paths. **Closure proof:** one focused executable-root-policy fixture exercised through cold build and public PR context, plus an update/warm control, shows the affected source excluded for the attribute reason; ordinary mode `100644` and missing policy retain their outcomes.
