## TASK-A-1 — Fetched PR source bypasses the configured file ceiling

- **Classification:** INCORRECT / VIOLATION. **Defect class:** source size is accepted from optional tree metadata and not rechecked against the PR file limit after a verified blob fetch. The optional `TreeEntry::size` shape permits this; the PR facade's own fetched-blob paths fail to enforce the advertised limit.
- **Root cause and siblings:** `eligibility::exclusion` accepts an otherwise eligible file when `entry.size` is `None` (`eligibility.rs:278`). `PrContext::changed_head` then fetches and returns the bytes, and may index them through `Ingest::ingest`, without checking `limits.max_file_bytes` (`pull_request.rs:416–430`). `PrContext::pack` likewise inserts a selected candidate's fetched bytes into the packing view without that check (`pull_request.rs:465–476`). The shared `Ingest::ingest` also has no byte-size guard (`snapshot.rs:973–978`); its fallback caller checks size first, but the PR changed-head caller does not. These are the changed-head analysis/index and selected-candidate packing siblings of one size-validation gap.
- **Obligation and reachability:** The approved spec defines eligible files as initially at most 1 MiB, REQ-013 requires file-size and memory bounds, and `PrContextLimits::max_file_bytes` states “Largest eligible file.” Supply a valid pinned head tree with a supported file whose `size` field is omitted, a valid SHA, and blob bytes larger than a configured `max_file_bytes` yet within `GitHubClient::RequestLimits::max_blob_bytes` (for example 2 KiB under a 1 KiB PR limit). An ordinary changed patch makes `changed_head` analyze and possibly index it. An oversized unchanged candidate can be ranked by another changed head and fetched into `pack`. Both paths are reachable through public `PrContext::run` with verified provider bytes; SHA verification does not establish the configured size limit.
- **Consequence:** The PR invocation processes source above its configured file ceiling; it can include an over-limit changed head in ranking and an over-limit candidate in the stored context. The caller receives neither an oversize exclusion nor a file-local omission. With many such entries, work exceeds the declared per-file bound even though the pipeline tests remain green.
- **Testable correction:** Enforce the configured size ceiling on actual fetched bytes at the PR source-admission owner for both changed heads and selected candidates, using existing oversize/not-analyzed and coverage reporting. Keep valid under-limit blobs, file-local continuation, selected candidate ranking, and verified blob identity. A focused fake-provider test should omit `size` for a valid head and a candidate, set `max_file_bytes` below their verified byte lengths but within client transport limit, and assert neither oversized source enters ranking/index or selected spans, with explicit reasons; include an under-limit control. This does not require a new abstraction or dependency.
