## Proposed findings

### DOM-TRUST-R3-1 — cancellation can still publish after snapshot read-back

- **Classification:** INCORRECT; prior `FIND-TASK-003-2` class remains incomplete. **Defect class:** the execution guard ends before the publication IO boundary. The owner is `ColdBuild::run`/`ColdBuild::publish`, not a provider caller or the archive reader.
- **Siblings:** cancellation or deadline expiry during `record_snapshot`, `storage.create`, or `storage.read` at `snapshot.rs:581-590` reaches the same unguarded pointer publication at `snapshot.rs:600-605`. A cancellation after `run`'s final check at `snapshot.rs:525` and before `publish` starts does too. The reused-pointer path at `snapshot.rs:465-472` can likewise return `Reused` after its storage read was cancelled.
- **Obligation:** spec REQ-005 says the cold-build call honors caller cancellation and deadline; REQ-013 requires honest cancellation and bounded invocation duration. R1 FIND-2 required a final pre-publication check. `Execution::check` observes cancellation and deadline but no check is made after read-back or immediately before the pointer CAS.
- **Evidence and consequence:** a caller can cancel while an injected storage `read` is blocked. When it returns valid bytes, `publish` advances the pointer and `run` reports `Published` despite cancellation; the reusable snapshot becomes visible after the caller requested interruption. This is reachable from the public `ColdBuild::run` with a storage implementation that cancels the shared token before returning from `read`.
- **Testable correction:** check the execution immediately before the pointer publication, carrying interruption into the existing incomplete outcome and leaving any already written object recorded for collection. Also ensure a reused-pointer read cannot report success after cancellation. A controlled storage double should trip the token during read-back and show unchanged prior pointer plus an interrupted result. No new storage trait or timer abstraction is needed.

### DOM-TRUST-R3-2 — `.gitattributes` reset is interpreted as an explicit false override

- **Classification:** INCORRECT. **Defect class:** the root-attribute parser collapses Git's three states (`set`, `unset`, `unspecified`) into two booleans. The owner is `parse_attribute` in `eligibility.rs`, whose result drives `RootAttributes::resolve` and `exclusion`.
- **Siblings:** both `!linguist-vendored` and `!linguist-generated` are parsed as `false`; the resulting false suppresses the built-in vendored-segment or minified-output exclusion at `eligibility.rs:279-283`.
- **Obligation:** spec eligible-file definition and TASK-003 approach require root `.gitattributes` overrides to apply. Git `!attr` resets an attribute to *unspecified*, so built-in exclusions must still apply when no explicit override remains.
- **Evidence and consequence:** `git check-attr linguist-vendored -- vendor/a.ts` in a temporary repository with `vendor/* !linguist-vendored` returns `unspecified`. Candidate `parse_attribute` returns `("linguist-vendored", false)` and `exclusion` therefore indexes `vendor/a.ts` despite the `vendor` exclusion. The same pattern admits `app.min.js` after `!linguist-generated`, making eligibility and coverage wrong for ordinary Git attributes.
- **Testable correction:** preserve the unspecified state when parsing and applying a reset, then allow normal path/output exclusions to run. Add one focused classification test for both reset cases, alongside explicit `-attr` cases that still override those exclusions.

## Verification limits and result

I did not mutate the candidate or run a compiled scratch test for the storage-cancellation path; the orchestrator can reproduce it with a controlled storage double. Existing R2 owner tests demonstrate archive-read cancellation, not interruption during publication IO. **Overall: FAIL** on the two proposed task-contract findings.
