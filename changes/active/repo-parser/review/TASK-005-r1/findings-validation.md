## Blocking ledger

### FIND-TASK-005-1 — Existing context objects are accepted without validation

- **Claims/status:** TASK-A-1, TASK-B-2, CTX-D-2 — **CONFIRMED**. **Gate:** absolute source-integrity boundary and TASK-005 immutable publication/read-back contract. **Class/root cause:** `Contexts::publish` treats `ObjectStorage::create`'s `AlreadyExists` as proof of content equality although the storage trait says only that the key is taken. The digest-derived key does not authenticate bytes already stored there.
- **Trace and siblings:** Public `PrContext::run` calls `Contexts::publish` (`pull_request.rs:282-289`); it upserts the record first (`context.rs:305-315`) and returns success for `AlreadyExists` (`context.rs:316-319`). `Contexts::read` then rejects a different digest (`context.rs:355-365`). The same storage condition in snapshot publication is already handled by reading and comparing bytes (`snapshot.rs:703-711`). The publication result and later shared read are both affected; there is one owner, `Contexts::publish`.
- **Reproduction:** Given a context's digest key already containing other bytes, `create` returns `AlreadyExists` by contract (`storage.rs:216-228`), `publish` returns its new record, and `read` returns `Corrupt`. This is reachable through the public PR facade with an injected storage implementation or a corrupt existing object; a successful publication can be unreadable.
- **Correction/proof:** In the `AlreadyExists` arm, read the exact key and compare the bytes with the serialized context before returning success, as snapshot publication does. Propagate read failure or `Corrupt` on mismatch. A focused test preloads different bytes at the exact key, calls publication, and requires an error; equal bytes must still support retry.

### FIND-TASK-005-2 — Distinct publications alias one context ID and cleanup target

- **Claims/status:** TASK-A-2, TASK-A-3, TASK-B-3, CTX-D-1 — **REVISED and merged by root cause**. **Gate:** 24-hour read cutoff (`spec.md` REQ-014, INV-005; TASK-005 Scenario 3) and durability/concurrent publication boundary. **Class/root cause:** the ID is solely the serialized-byte digest (`context.rs:298-306`), while each publication replaces its record with a new expiry (`context.rs:313-315`, `persistence.rs:243-253`). A logical new publication and an older published ID are indistinguishable to reads and cleanup.
- **Trace and siblings:** `PrContext::run` publishes at the current time (`pull_request.rs:282-289`); `read` authorizes by the current record's expiry (`context.rs:342-354`); `collect_expired` takes a copied expired record then deletes by key and ID (`context.rs:394-403`). `MemoryContextStore` replaces the row by `(identity,id)` (`testing.rs:403-412`), returns copied expired rows (`testing.rs:439-452`), and deletes the current row by ID without comparing expiry (`testing.rs:460-468`). The old ID's read lifetime, fresh publication success, object deletion, and record deletion are siblings of the same aliasing error.
- **Reproduction:** Publish bytes at `t0`, publish identical bytes at `t0+1h`: both results have the same ID; a read using the original ID at `t0+24h` succeeds because its record now expires at `t0+25h`. For the race, let `expired_contexts` copy the `t0` row at `t0+24h`, republish the identical context, then resume collection: it deletes the fresh object's key and fresh record. If publication occurs after object deletion but before stale record deletion, publication succeeds with an object but the collector removes its row. Neither current test serializes these interleavings.
- **Correction/proof:** Keep the per-publication 24-hour lifetime by deriving each context ID and object key from both the content digest and the publication timestamp supplied to `publish`; retain the digest separately for read integrity. Equal content published at different times then has different cleanup targets. A repeated attempt at the same timestamp is create-if-absent idempotent; a dropped `PrContext::run` retried later may return a new ID, which still converges to a readable context. Its earlier record/object remains paired and expires on its own schedule. Preserve record-before-object order, exact-key tenant checks, and object-then-record cleanup. Focused paused-clock tests publish identical content at two times, require distinct IDs, check the first expires at its original cutoff and the second remains readable, and pause cleanup after listing the first before publishing the second; only the first may be deleted. Also drop a publication after record upsert and after object create, retry `PrContext::run` with a later clock time, and require a readable returned ID plus no unrecorded object.

### FIND-TASK-005-3 — Scoped file limit is spent on excluded entries

- **Claims/status:** TASK-B-1, BUDGET-1 — **CONFIRMED**. **Gate:** production path gives wrong scoped candidates and REQ-008's bounded *eligible* files. **Class/root cause:** `near` applies `take(max)` to raw nearby file/executable tree entries (`pull_request.rs:543-551`) before `Ingest::new` runs the shared eligibility classification (`pull_request.rs:180-190`, `snapshot.rs:769-790`, `eligibility.rs:244-261`).
- **Trace and siblings:** Failed/no compatible snapshot enters scoped mode in `PrContext::run`; its `near` output is the entire ingest input. Generated, vendored, unsupported, and oversized entries can all pass `near`'s mode/directory filters but are excluded by `eligibility::exclusion` (`eligibility.rs:265-297`). Changed files are prioritized, so a changed excluded file can consume the limit too. A nearby eligible symbol source beyond those raw entries is absent from ranking, while coverage counts only the selected slice.
- **Reproduction:** Set `max_scoped_files=2`, put a changed eligible file and an unsupported neighbor before an eligible same-directory candidate. `near` returns the first two; classification excludes the neighbor, so the useful candidate is never indexed or selected. A full snapshot with the same tree could select it.
- **Correction/proof:** Reuse `eligibility::classify` on the nearby tree entries before applying the scoped eligible-file ceiling; keep bounded fetches and explicit scoped coverage, including exclusions, without treating excluded paths as consuming eligible slots. A focused scoped PR test places each exclusion class ahead of an eligible matching neighbor at a low ceiling and requires that neighbor to enter the index/ranking while the eligible bound holds.

### FIND-TASK-005-4 — Rejected provider entries can coexist with full coverage

- **Claims/status:** SRC-1 — **CONFIRMED**. **Gate:** source-trust/coverage boundary and REQ-009–010, INV-002 (honest coverage). **Class/root cause:** rejected PR-file entries are recorded only as `NotAnalyzed`, while `ContextCoverage::is_full` ignores them; rejected tree entries are counted as exclusions even though their eligibility is unknown.
- **Trace and siblings:** `GitHubClient::pull_request_files` rejects invalid file records (`github.rs:1141-1157`). `pin` retains the rejection (`pull_request.rs:303-315`), and `run` records it in `not_analyzed` (`pull_request.rs:199-208`) but sets `pr_files_truncated` only from pagination and `overlay_complete` from indexed entries (`pull_request.rs:219-232`). `is_full` checks neither rejected count nor `not_analyzed` (`context.rs:57-65`). The tree path passes `listing.rejected.len()` to `Ingest` (`pull_request.rs:169-176`); `Ingest::finish` counts those as `InvalidEntry` exclusions (`snapshot.rs:994-1010`), and `Coverage::is_complete` ignores exclusions (`snapshot.rs:130-134`). Rejected invalid SHA/status/previous path and rejected tree entries are sibling sources of unknown coverage.
- **Reproduction:** A full valid snapshot/head tree with one PR-file wire entry that fails validation yields one `NotAnalyzed::Rejected` but all `is_full` inputs can remain true. Conversely, a rejected tree entry with an otherwise indexed valid tree contributes only `InvalidEntry` exclusion and allows `is_complete`, so a candidate may be falsely absent under declared full coverage.
- **Correction/proof:** Carry a rejected-entry completeness signal from both provider lists into the existing coverage axes. Rejected PR files must make PR coverage partial; rejected tree entries must make snapshot/overlay completeness partial unless they can be proved ineligible from validated path/mode facts. Preserve the diagnostic `NotAnalyzed` and excluded counts. Focused tests inject one invalid PR file and one invalid tree entry separately and assert `!is_full`, while an ordinary validated unsupported path remains a benign exclusion.
