## Proposed findings

### CTX-D-1 — Cleanup can delete a concurrently renewed context

**Classification:** INCORRECT; durability / retry safety. **Defect class:** context cleanup selects an expired row without claiming it, while publication unconditionally replaces the same `(identity,id)` row. The candidate-owned `ContextStore` shape permits a stale expiry listing to authorize deletion after renewal. **Owner:** `ContextStore::expired_contexts`/`upsert_context` contract and `Contexts::collect_expired`, with the in-memory implementation carrying the same pattern.

**Obligation:** TASK-005 lines 49 and 59 require a dropped/retried PR call to converge on a readable context and cleanup to remove contexts past `expires_at`; spec REQ-012 and REQ-014 require retry-safe publication and no read before the renewed 24-hour lifetime ends. The content digest makes the same review republish the same ID. `upsert_context` replaces its row, `expired_contexts` returns a snapshot of rows, and `collect_expired` deletes by key and ID without checking whether that row is still expired.

**Reachable interleaving:** Existing context `K` is expired. Collector lists its record and pauses. `PrContext::run` publishes the same context bytes: `upsert_context` refreshes expiry and `create` reports `AlreadyExists`, so run returns success with `K`. Collector resumes, deletes `K`'s object and record. The fresh result is immediately unreadable. A second ordering is worse: collector deletes the object, publisher upserts and creates, then collector deletes the renewed record, leaving an unrecorded source-bearing object. Both interleavings use the supplied in-memory trait implementation; no unusual storage behavior is needed. Sequential cleanup tests do not exercise this. **Sibling sinks:** object deletion and record deletion in `collect_expired`; success return from `Contexts::publish` and `PrContext::run`.

**Testable correction:** Make expiry collection and renewal coordinate at the context-record owner so a collector cannot act on a row renewed after selection, and a publisher cannot reuse an object being deleted. Preserve object-before-record deletion and record-before-object creation. A focused concurrent test should hold a collector after selection, republish the same content, release collection, and assert the returned ID stays readable with a record and one object; repeat at the object-delete/record-delete boundary.

### CTX-D-2 — Existing object is accepted without validating its bytes

**Classification:** INCORRECT; context integrity. **Defect class:** `AlreadyExists` is treated as successful publication without checking the existing object's digest. **Owner:** `Contexts::publish`; its shape has an unchecked success branch. The task requires publication of a complete, validated immutable context object, and scenario 3 requires a retry to return a readable context. `ObjectStorage::create` promises only that the key is taken; the crate says integrity is checked by the library, not the backend. A corrupted or wrong object under the deterministic key makes a later identical publication upsert a fresh row and return success, while `Contexts::read` immediately returns `Corrupt`. A normal prior publication followed by object corruption and a later repeat of the same PR is a reachable path; corruption is expressly part of TASK-005 scenario 3. **Sibling sinks:** the `AlreadyExists` success branch and the `PrContext::run` success result. The normal fresh-create branch is not implicated.

**Testable correction:** On `AlreadyExists`, read the exact object and verify its digest and context identity before reporting publication success; a mismatch must be an explicit failure or be repaired through a safe, specified replacement path. Add a focused test that corrupts the existing object, republishes the same context, and asserts no successful ID for unreadable bytes.
