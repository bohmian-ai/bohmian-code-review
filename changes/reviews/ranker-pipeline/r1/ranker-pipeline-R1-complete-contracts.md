## Diagnosis and required outcome

### FIND-ranker-pipeline-1 — caller supplied evaluation inputs

`trial::evaluate` in `crates/bohmian-code-review-eval/src/trial.rs:297-318` does not accept named `&dyn Ranker` arms, and `trial.rs:37-42,261-281` uses a fixed S/C/E/F set. `live.rs:53-85,372-433,473-485` selects only internally configured repositories/PRs; `live.rs:530-539` and `report.rs:113-120` compute effects from fixed arms. These are siblings of one input-shape defect. Decision 3 requires a reusable harness taking a repository sample and named rankers. The existing passing eval tests exercise the fixed experiment, so they do not prove the required consumer call. A caller cannot evaluate a custom sample or ranker without changing crate source.

Make the existing evaluation workflow accept a caller supplied repository sample and named public `Ranker` references through trials, per-PR means, paired differences, seeded bootstrap, decision rule, and report output. Keep the live S/C/E/F choice in the thin binary and preserve the checked-in C/E/F report shape and values. Reuse public rankers and the current trial/report owners; do not introduce a second ranking implementation or parallel harness. The exact candidate-owned input representation can change. A public consumer test must pass a small sample and at least two named caller rankers and observe their named hit@10 and decision output.

### FIND-ranker-pipeline-2 — complete, stable history discovery

`CoChangeHistory::read` in `crates/bohmian-code-review-pipeline/src/history.rs:385-386` stops after ten pages and `:413-417` can return `Ok` without proving cold depth or reaching the prior snapshot boundary. The existing test at `history.rs:677-714` expects success with ten `has_next=true` pages and an unjoined prior history. The same reader checks only the first page-one entry at `history.rs:407-410`; a lower item can move from page two into page one while that first entry stays fixed, so a merged PR can be omitted from the traversed pages. The provider page is produced in `github.rs:1494-1568`; both `snapshot.rs:739-752` and `update.rs:120-124` consume the successful result and may publish it. Decision 7 requires bounded, complete-or-fail history for cold build and update. The current cap and first-entry tests do not prove that contract.

Correct completeness once in the shared history reader, using the existing pipeline GitHub provider owner. A bound reached while `has_next` advertises more data must fail unless the required cold depth or prior boundary was proved. A multi-page read must detect a changed traversed listing, including movement below the first entry, and fail as a retry state before either publication path. Keep the ten-page bound, genuine empty-history success, mass-edit exclusion, source-free records, and 1,000-PR retention. Preserve the prior history only after a proved join. The provider's existing page result may carry more listing identity if needed; do not add an independent provider or a second history workflow.

Focused fake-provider proof must cover cold build and update with an unproved cap and no published replacement pointer, genuinely exhausted empty history, and a page-two item moving into page one below the unchanged first item. The moving listing must fail without publishing. Exercise both facade publication paths through the shared reader.

### FIND-ranker-pipeline-3 — pipeline-owned provider reads

The eval `Api` in `crates/bohmian-code-review-eval/src/live.rs:147-189` holds a raw transport and token and builds authenticated REST GET requests. Its sibling sinks are repository discovery (`live.rs:377`), PR listing (`:387-391`), and base commit time (`:244-249`); `live.rs:452-463` constructs both this direct client and `GitHubClient`. `AGENTS.md:23` and the architecture assign Git provider IO to the pipeline crate and require eval to read through pipeline types. Every live run reaches the direct discovery/listing path, while sampled trials reach base time. The no-network eval test passing does not make this ownership valid.

Route all three reads through concrete pipeline provider operations. Reuse `GitHubClient::commit` for base time and existing repository validation where applicable; add only the narrow pipeline-owned discovery/listing operations the live sample needs. Remove the eval-local raw transport, token ownership for HTTP, request construction, and REST response decoding. Preserve sample selection, bounded provider behavior, and report results. A fake transport test must exercise all three operations through `GitHubClient`, including identity checks and provider error handling; a source boundary check must find no raw provider request path in eval.
