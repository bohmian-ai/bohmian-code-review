### FIND-ranker-pipeline-2 — REVISED (merged)

- **Wave 1 IDs:** TASK-A-2, DOMAIN-HISTORY-1, DOMAIN-HISTORY-2. **Gate:** task contract and absolute history integrity. **Class:** INCORRECT. **Defect class:** `CoChangeHistory::read` can return success without proving that discovery reached the required boundary across a stable paginated listing.
- **Obligation:** decision 7 of `changes/reviews/ranker-pipeline/intent.md:13` requires bounded, complete or fail cold and update history; empty history is valid only when genuinely discovered empty. `architecture/agent-rules.md:7` prohibits turning omission into apparent success.
- **Owner and siblings:** `crates/bohmian-code-review-pipeline/src/history.rs:385-386` ends at ten pages with `break false` even when the cold depth or prior snapshot boundary is unproved; `history.rs:407-410` rechecks only the first item of page one after multi page discovery; `history.rs:413-417` drops prior history when `joined` is false, truncates, and returns `Ok`. The source page comes from `github.rs:1494-1568`, which sorts by mutable `updated_at`, exposes `has_next`, `first`, and `oldest_update`. The two production callers are `snapshot.rs:739-752` (cold and fallback build) and `update.rs:120-124` (incremental update); both use the returned history in a publish path.
- **Independent reproduction, cap:** `history.rs:677-714` already constructs ten pages with `has_next=true`, no merged entries, and a prior boundary not reached, then asserts `read(...).await.expect("history")` returns an empty `prs`. The same branch can occur on cold build with fewer than ten qualified entries. `snapshot.rs:710-729` and `update.rs:120-124` accept that `Ok` and continue. This is direct executable evidence of a partial history being treated as complete.
- **Independent reproduction, moving pages:** `closed_pull_requests` queries `state=closed&sort=updated&direction=desc` with numeric pages (`github.rs:1494-1504`). With 100 entries per page, read original items 1–100 on page one. Before page two, original item 101 is updated and moves to position 2; original item 1 remains first. The new page two begins with original item 100, so item 101 was on neither page as read. The reread compares only item 1, so `history.rs:409` accepts and `history.rs:417` returns success. A merged omitted item can be between `before` and the prior boundary, so the published history silently misses it. The existing `listing_changed_mid_read_fails` test changes the first item only (`history.rs:599-609`) and does not cover this reachable sibling.
- **Consequence:** cold build or update can persist a source free snapshot with missing co change PRs and later F ranking can select the wrong files; update may also discard its prior history without reaching the prior boundary.
- **Minimal correction:** fix completeness in the shared `CoChangeHistory::read` owner. Treat an advertised next page at the discovery bound as an error unless cold depth or the prior boundary has already been proved; retain the prior history only after a proved join. For multi page reads, use the existing `GitHubClient::closed_pull_requests` endpoint to recheck the traversed pages, comparing enough page identity and update data to detect changes beyond the first item; fail as a retry state on a mismatch. This may require carrying the page's full ordered IDs and update times through `ClosedPullRequestsPage`, including unmerged entries; no new endpoint or generic provider interface is needed. Preserve the current ten page bound, legitimate empty history, mass edit exclusion, and 1,000 entry retention. **Closure proof:** focused provider fake cases (a) cap reached with `has_next` and no proved boundary, for both cold and update, fail without publishing, (b) genuine exhausted empty history succeeds, and (c) original item 101 moves into page one while page one's first item stays fixed and the read fails; run both public snapshot paths through the owner.

### FIND-ranker-pipeline-3 — CONFIRMED

- **Wave 1 ID:** DOMAIN-PIPE-2. **Gate:** repository standard. **Class:** VIOLATION. **Defect class:** the eval crate duplicates the authenticated provider IO boundary beside the pipeline client.
- **Obligation:** `AGENTS.md:23` explicitly says eval reads the provider only through pipeline types; `architecture/agent-rules.md:3,9` assign provider and source IO to the outer pipeline crate.
- **Owner and siblings:** `crates/bohmian-code-review-eval/src/live.rs:147-153` owns a direct `HttpTransport` and token; `live.rs:165-189` builds and sends raw authenticated GET requests. Direct GET sinks are repository discovery at `live.rs:377`, PR listing at `live.rs:387-391`, and base commit time at `live.rs:244-249`. `live.rs:452-463` creates both this direct transport and a pipeline `GitHubClient`.
- **Independent reproduction:** trace `live::run` (`live.rs:473-485`) to `Api::select`, then `Api::get` at the repository and paged PR listing sinks; `Api::qualify` reaches `base_time` and its `Api::get`. Each reaches `self.direct.get(HttpRequest { authorization: Bearer ... })`, bypassing `GitHubClient`. This is an unconditional live path, not test only. Existing `GitHubClient::commit` already supplies the validated committer time (`github.rs:1084-1112`); `GitHubClient::repository` supplies validated repository metadata after identity is known (`github.rs:1026-1048`).
- **Consequence:** the eval crate owns raw credential handling and provider request policy contrary to the written ownership boundary; its behavior can diverge from the pipeline's identity and response validation.
- **Minimal correction:** route these three reads through concrete pipeline types, reusing `GitHubClient::commit` for base time and its existing repository validation where applicable. Add only the narrow pipeline owned repository discovery and PR listing operations needed by the live sample, with the pipeline's transport, limits, and validation; remove `Api`'s raw transport, token, and direct GET implementation. Keep the fixed live sample and report behavior. **Closure proof:** a source boundary check finds no direct `HttpTransport::get`, `HttpRequest`, token held for HTTP, or raw provider URL in eval; a fake transport test exercises all three reads through `GitHubClient`, including the existing commit identity check and a non 200 or oversized response failure.
