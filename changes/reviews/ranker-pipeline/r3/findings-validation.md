- **Obligation:** intent decision 7 requires complete-or-fail bounded history and extension since the prior snapshot; `architecture/bohmian-code-review-design.md:22` requires update to prepend newly merged PRs to prior history, and `architecture/agent-rules.md:7` forbids apparent success after omission.
- **Owner, callers, and siblings:** `CoChangeHistory::read` at `crates/bohmian-code-review-pipeline/src/history.rs:368-436` owns both cold and incremental completion. At `:399-406`, reaching ten pages with `has_next` accepts `history.prs.len() >= COLD_DEPTH` even when `since` is set and `joined` remains false; `:432-435` then drops the prior records and returns `Ok`. Its direct callers are `ColdBuild::history` (`snapshot.rs:739-752`) from direct build and update fallback (`snapshot.rs:723`, `update.rs:120-122`), and incremental update (`update.rs:124`). `ColdBuild::complete` and `Update::run` can publish that history; PR context loads the snapshot (`pull_request.rs:223-229`) and filters the incomplete history (`pull_request.rs:448-463`). The `known`/`horizon` proof and page re-read at `history.rs:372-429` do not establish a prior join at this cap.

Advertise `has_next=true` on page ten, let each PR have at most 30 changed files, and keep every `merged_at` above prior `before`. The shared reader increments `history.prs.len()` to ten, reaches `:399`, takes `break false` at `:406`, omits `prior.prs` at `:432`, and returns success. This path is reachable through both publish callers above. Existing `empty_history_is_valid_and_an_unproved_bound_fails` (`history.rs:687-735`) tests only `found: 0`, so it cannot catch this case.
- **Consequence:** a refreshed snapshot silently loses older co-change records and subsequent fused ranking can choose different files for a PR whose base precedes the new snapshot.

Preserve the cold build's ten-PR stopping rule, the ten-page bound, stable-listing check, mass-edit exclusion, 1,000-entry retention, and existing publication lifecycle. ### FIND-ranker-pipeline-4 — CONFIRMED

- **Source:** TASK-B-1. **Gate:** task contract. **Classification:** INCORRECT. **Defect class:** persisted reference-name facts bypass the record's validation boundary.
- **Obligation:** intent decision 4 requires *distinct* persisted reference and extractor-candidate names; `architecture/bohmian-code-review-design.md:36` says loading malformed facts fails explicitly while leaving other files intact.
- **Owner, callers, and siblings:** `IndexedFileFacts::validate` (`crates/bohmian-code-review-core/src/facts.rs:119-129`) checks declarations only, although `references` is an ascending, distinct names field (`:111-113`). `SymbolIndex::load` (`index/src/lib.rs:217-225`) trusts that result then collects references into a `BTreeSet`, silently accepting duplicate or out-of-order names and posting an empty name. `SymbolicContext::load` (`bohmian-code-review/src/lib.rs:230-241`) is the public facade caller. Snapshot `into_context` (`pipeline/src/snapshot.rs:329-343`) and carry/reuse (`:1047-1058`, `:1172-1182`) are its pipeline siblings. The normal producer `SymbolicContext::upsert` (`bohmian-code-review/src/lib.rs:178-188`) uses a `BTreeSet`; `IndexedFile::export` (`index/src/lib.rs:38-50`) exports its sorted, distinct names, so validating this invariant accepts genuine records.
- **Independent reproduction:** Construct `IndexedFileFacts` with the current extraction version and an otherwise valid declaration, but `references = vec!["x".into(), "x".into()]` or `vec!["".into()]`. `IndexedFileFacts::validate` returns `Ok`; public `SymbolicContext::load` succeeds. Duplicate names are silently collapsed; an empty name remains queryable through `SymbolIndex::referencing("")`. This contradicts explicit malformed-fact failure even though current valid producer output is unaffected.
- **Consequence:** a malformed persisted snapshot can be accepted as complete, and corrupt reference postings can influence candidate-file ranking instead of producing a typed load failure.
- **Minimum correction:** enforce the existing exported representation's nonempty, strictly ascending reference names in `IndexedFileFacts::validate`, before `SymbolIndex::load` mutates the file. Reuse its `InvalidFact` error path and public facade mapping. Keep declarations, extraction-version checks, source-free projection, and unrelated snapshot recovery behavior.
- **Focused closure proof:** one public load check rejects empty, repeated, and unordered reference names without changing an existing file's postings; a real extracted/exported record still round-trips. A decoded snapshot's `into_context` path must reject the same malformed facts.

### FIND-ranker-pipeline-5 — CONFIRMED

- **Source:** DOMAIN-PROVIDER-1. **Gate:** absolute source-trust boundary and repository standard. **Classification:** VIOLATION. **Defect class:** the shared listed-PR conversion discards base repository identity before its consumers can verify it.
- **Obligation:** `architecture/bohmian-code-review-design.md:5,22` and `AGENTS.md:23` assign Git identity verification to the pipeline provider. R1 FIND-3 requires provider-owned identity checks for the eval listing; a single-PR read already enforces the same base-repository rule (`github.rs:1460-1482`).
- **Owner, callers, and siblings:** `ListedRefWire` (`crates/bohmian-code-review-pipeline/src/github.rs:749-753`) has only ref and SHA; `listed_pull_request` (`:868-899`) cannot compare a base repository ID. Both `closed_pull_requests` (`:1588-1610`) and `pull_requests` (`:1686-1691`) use it. The former feeds `CoChangeHistory::read` (`history.rs:408-415`) for cold/update snapshots; the latter feeds eval sample selection (`bohmian-code-review-eval/src/live.rs:277-285`). `GitHubClient::pull_request` shows the existing policy and wire representation, requiring `base.repo.id == repository.id()` (`github.rs:1467-1482`). The R1 fake-provider listing test (`github.rs:2178-2229`) actually uses base refs without `repo`, so it would pass a missing identity.
- **Independent reproduction:** A listed PR response with `base.repo` absent or carrying a different numeric ID still deserializes into `ListedRefWire`, is converted successfully, and enters closed history or eval. The request URL's repository name identifies the endpoint, not each returned entry. This is a reachable provider trust boundary, not a speculative downstream caller.
- **Consequence:** another repository's or an identity-less PR entry can supply commit IDs and changed paths to persisted history or evaluation, contrary to the repository's verified-source requirement.
- **Minimum correction:** in the existing shared listed-PR wire/conversion path, carry and require the base repository ID and compare it with the requested `RepositoryIdentity` before either page returns entries. Reuse the single-PR `IdentityMismatch` semantics; preserve head-fork behavior, page bounds, branch checks, and eval sample policy. No separate eval guard or new provider is needed.

Update current valid listed-PR fixtures to supply the real base identity.
