## Diagnosis and correction

### FIND-ranker-pipeline-2 — incremental history may succeed without joining its prior

`CoChangeHistory::read` in `crates/bohmian-code-review-pipeline/src/history.rs:399-406` accepts a ten-page cap with more pages advertised whenever ten qualifying PRs were read, including an incremental read that has not reached `prior.before`. It then drops the prior records at `:432-435` and returns success. This is the same incomplete-discovery class as R1 FIND-2: R1's count guard corrected the fewer-than-ten case but leaves the incremental completion rule shaped around cold depth. Ten pages with one new eligible PR each, an eleventh unseen new merge, and an older prior boundary reach this branch. `Update::run` consumes it directly at `update.rs:124` and through fallback build at `:120-122`; `ColdBuild::build` accepts it at `snapshot.rs:723`, `ColdBuild::complete` can publish it at `:855`, and PR context consumes the persisted history at `pull_request.rs:448-463`. The existing cap test uses zero qualifying PRs and does not exercise this branch. A successful refresh can therefore discard prior history and omit new merges, violating intent decision 7 and the complete-or-fail rule.

Correct the completion rule once in the shared reader: an incremental read succeeds only after it proves the prior boundary or genuine listing exhaustion; cold reads may still complete after ten qualified PRs. An unproved advertised next page must fail before either publication sink, regardless of the count of newly found PRs. Preserve the ten-page bound, page stability rechecks, source-free records, mass-edit exclusion, 1,000-entry retention, and the existing update and fallback publication lifecycle. A proved join still prepends new records to the prior history. The candidate-owned reader already has the prior boundary and typed `UnprovedHistory` error; reuse them.

### FIND-ranker-pipeline-4 — persisted reference names bypass fact validation

`IndexedFileFacts.references` promises sorted distinct names (`crates/bohmian-code-review-core/src/facts.rs:111-119`), but `IndexedFileFacts::validate` at `:128` validates only declarations. `SymbolIndex::load` at `index/src/lib.rs:218-224` therefore accepts empty, duplicate, or unordered names, silently collapses duplicates into a set, and can create an empty-name posting. The public `SymbolicContext::load` at `bohmian-code-review/src/lib.rs:230-241` and pipeline snapshot read/carry at `snapshot.rs:329-343,1047-1058,1172-1182` share this validation boundary. Current extracted/exported facts are sorted and distinct, so the existing valid round-trip test passes; it cannot prove malformed-fact rejection. Acceptance contradicts intent decision 4's distinct persisted names and the design's explicit failure rule for malformed facts.

Enforce nonempty, strictly ascending reference names in the existing `IndexedFileFacts::validate` owner, before any index replacement. Reuse `InvalidFact` and the existing public load error mapping; do not normalize an invalid persisted record into success. Preserve declaration checks, extraction-version rejection, source-free export, and file-local atomic replacement. A public facade load proof must reject empty, repeated, and unordered names while keeping existing file facts and postings; a real exported record must round-trip. Snapshot read-back must reject malformed persisted names rather than report complete coverage.

### FIND-ranker-pipeline-5 — listed PR base repository identity is discarded

`ListedRefWire` at `crates/bohmian-code-review-pipeline/src/github.rs:749-753` drops `base.repo.id`. Consequently `listed_pull_request` at `:868-899` cannot verify it against the requested repository. Both `closed_pull_requests` at `:1595-1605` and `pull_requests` at `:1686-1691` accept the conversion. Closed listing feeds cold/update history (`history.rs:408-415`); all-PR listing feeds eval sampling (`bohmian-code-review-eval/src/live.rs:277-285`). A response with absent or mismatched base repository id is accepted, while the single-PR provider reader already rejects it at `github.rs:1460-1482`. The current fake listing fixture omits `base.repo` and passes, so it conceals the gap. This breaks the pipeline's written Git identity verification boundary and can admit foreign paths into persisted history or evaluation.

Carry and require the base repository id at the shared listed-PR conversion boundary, comparing it with the requested `RepositoryIdentity` before returning either page. Reuse the existing single-PR `PullRepoWire` and `IdentityMismatch` policy. Preserve head-fork handling, branch and commit validation, page bounds, and eval selection behavior. Fake-provider proof must reject missing and mismatched base ids in both listing operations, accept matching base identity even when the head is a fork, and show a rejected closed listing publishes no history. Update valid fake responses to include the required base identity.
